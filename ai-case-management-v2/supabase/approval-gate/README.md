# 승인 게이트 (소속 변경 → 승인 대기 / 역할·승인·기관정보 관리자 전용)

앱 코드는 바뀌지 않습니다. Supabase SQL Editor 에서 아래 순서로 **한 파일씩** 실행합니다.

| 순서 | 파일 | 하는 일 | 앱 동작 변화 |
|---|---|---|---|
| 0 | `00_precheck.sql` | 읽기 전용 점검 | 없음 |
| 1 | `01_install.sql` | 설치 + **관찰 모드**(기록만, 막지 않음) | 없음 |
| – | (직접 확인) | 아래 체크리스트로 평소처럼 사용 → `04_check_log.sql` 로 기록 확인 | – |
| 2 | `02_enforce.sql` | **실제로 막기 시작** | 아래 4가지 규칙 적용 |
| – | `03_rollback.sql` | 언제든 완전 원상복구 | 설치 전과 동일 |

## 적용되는 규칙 (2단계 이후)
1. 사용자가 직접(앱/API) 소속 기관을 바꾸면 **자동으로 `pending`** 이 된다. 클라이언트가 `approved` 를 같이 보내도 무시된다.
   - 예외: 내가 방금 만든 기관(나 외에 구성원 없음)은 승인 없이 시작.
   - `join_org_by_code` RPC 로 가입해도 곧바로 `pending` (앱의 후속 upsert 에 의존하지 않음).
2. `pending` 계정은 `current_org_id()` 가 NULL → 대상자·상담 등 **모든 데이터 읽기/쓰기 불가**. 자기 프로필은 읽을 수 있어 대기 화면은 그대로 표시.
3. `status` 변경은 **그 기관의 승인된 관리자만** 가능. 본인 승인 불가.
4. `user_roles` 추가/삭제/수정, `organizations` 수정은 **그 기관 관리자만**.

서버(service role)·대시보드·`assign_org_role`·`remove_org_member` 같은 시스템 함수는 영향 없음.
(로그인 정보 `auth.uid()` 가 있는 경우, 또는 API 직접 호출(`current_user = authenticated`)만 검사.)

## 즉시 해제 (문제가 생기면)
```sql
update guard.config set value = 'shadow', updated_at = now() where key = 'mode';
update guard.config set value = 'off',    updated_at = now() where key = 'data_block';
```
완전 복구는 `03_rollback.sql`.

## 클릭 체크리스트 (1단계 후 / 2단계 후 각각)
- [ ] 관리자 계정 로그인 → 대상자 목록·상담 저장·AI 기능 정상
- [ ] 일반 멤버 계정 로그인 → 정상
- [ ] 관리자: 구성원 탭에서 연락처 수정, 역할 변경, (테스트 계정) 내보내기
- [ ] 기관 코드로 가입(테스트 계정) → 승인 대기 화면 → 관리자가 승인 → 데이터 접근
- [ ] 가입 거절 → 계정이 기관 없음 상태로
- [ ] 새 기관 만들기(기관 없는 테스트 계정) → 바로 관리자로 사용 가능
- [ ] 본인 이름/연락처/결재선 수정
- [ ] 대기 중인 기존 계정은 계속 대기 화면
- [ ] 슈퍼관리자 `/admin` 화면 정상

`test/` 는 임시 DB(PGlite)에서 위 규칙을 64개 시나리오로 검증하는 스크립트입니다
(설치 전 구멍 재현 → 관찰 → 강제 → 롤백 원복). 프로젝트 의존성에는 포함되지 않습니다.
