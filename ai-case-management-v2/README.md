# 통합 사례관리 대시보드

사례관리 실무자의 기록 부담을 낮추고 누적 데이터를 AI로 분석하여, **한정된 복지 자원이 가장 필요한 사람에게 제때 닿을 수 있도록** 돕는 사례관리 솔루션

## 1. 팀 기본 정보

### 1.1 기관 정보

시립중랑노인종합복지관은 ‘덕불고필유린의 정신으로 모두가 은혜로운 하나의 세상을 만든다’는 미션 아래 지역사회 어르신들이 존엄한 노후를 보내실 수 있도록 힘쓰고 있습니다. 우리 기관은 평생교육과 취약계층 지원을 넘어, 의료·복지·마을이 연계된 민관협력 중심의 '돌봄통합지원'을 적극 추진하며 어르신들이 살던 곳에서 건강한 노후를 보낼 수 있도록 돕고 있습니다. 사별 어르신의 정서적 자립 프로그램인 ‘도란도란’, 아동성폭력예방을 위한 노인 봉사단 ‘빨간망토 인형극단’ 등 주체적인 사회 참여를 이끄는 특화 사업을 통해 세대가 상생하는 복지 공동체를 선도하고 있습니다.

## 2. AI 솔루션

### 2.1 문제 정의

시립중랑노인종합복지관 사례관리 담당자는 단 2명입니다. 이 두 사람이 사례관리 20명, 밑반찬 40명, 무료급식 286명, **총 339명의 취약계층 어르신을 전담**합니다. 담당자들이 바라는 것은 단 하나입니다. 한정된 복지 자원이, 진짜 필요한 어르신에게, 제때 닿는 것. 하지만 지금 시스템은 그것을 가능하게 하지 않습니다.

**[현장의 현실 : 기록할수록 지치고, 지칠수록 누군가가 빠집니다]**

하루에도 수십 명의 어르신과 나누는 대화를 빠짐없이 기록하는 것은 물리적으로 불가능합니다. 기존 진우시스템은 모바일을 지원하지 않고, 복지관 평가를 위해 정형화된 문장으로 작성해야 하는 기록 부담은 담당자를 지치게 만듭니다. 기록은 줄어들고, 줄어든 기록은 누락을 낳고, 누락은 판단의 공백을 만듭니다. **결국 '누가 더 시급한가'는 데이터가 아닌 담당자의 기억과 감으로 결정됩니다.**

이 공백이 만들어낸 결과는 실제로 확인됐습니다. 지난여름 폭염 대비 선풍기 후원을 배분할 당시, 파편화된 기록 탓에 담당자의 기억에 의존해 대상자를 선정했습니다. **그리고 사후에, 더 열악하고 더 시급했던 어르신이 명단에서 빠져 있었음을 확인했습니다.** 가장 필요한 사람이 가장 먼저 빠지는 역설. 이것이 지금 현장의 현실입니다.

이 문제는 저희 기관만의 이야기가 아닙니다. 타 기관 사례관리 실무 경험자 30명을 대상으로 자체 설문을 진행한 결과, **66.7%가 모바일 미지원으로 인한 현장 기록의 어려움**을 호소했습니다. 과거 기록의 검색·조회 제약과 데이터 요약 부재가 각 40%, 기록 작성 부담이 36.7%로 뒤를 이었습니다. *"축적된 기록에서 핵심 욕구를 한눈에 파악하기 어렵다", "수정할 때마다 삭제 후 재작성해야 한다"* — 현장의 목소리는 하나같이 같은 곳을 가리키고 있었습니다.

지금 시스템의 문제는 단순한 불편함이 아닙니다. **기록이 부담스러워 줄어들고 → 줄어든 기록은 누락되고 → 누락된 기록은 활용되지 못하고 → 결국 자원 배분은 주관에 의존하게 되는** 구조적 악순환입니다. 이 구조 안에서는 아무리 헌신적인 담당자라도 한계에 부딪힐 수밖에 없습니다.

**[솔루션 : 담당자의 판단을 기억에서 데이터로 바꿉니다]**

결국 이 모든 문제는 하나로 귀결됩니다. **담당자가 '누가 더 시급한가'를 데이터로 판단할 수 없다는 것.** 이것이 저희가 해결하고자 하는 핵심 문제입니다.

이번 솔루션은 두 단계로 문제에 접근합니다. 먼저 **AI 기반 상담기록 다듬기와 모바일 현장기록**으로 기록의 부담을 낮춥니다. 담당자가 현장에서 간단히 메모한 내용을 '다듬기' 버튼 하나로 **복지관 평가 기준에 맞는 정제된 상담기록으로 변환**할 수 있으며, **담당자가 AI의 초안을 직접 검토하고 수정한 뒤 최종 등록하는 구조**로 판단의 주체는 언제나 담당자에게 있습니다. 기록에 쏟던 시간과 에너지가 줄어든 만큼, 지금까지 누락되어 온 어르신의 욕구와 상태가 빠짐없이 데이터로 쌓이기 시작합니다.

축적된 데이터는 그 자체로 자산이 됩니다. **AI가 누적된 상담기록을 분석해 어르신별 욕구 변화와 긴급도를 도출**하고, 담당자는 이를 기반으로 누가 먼저 지원받아야 하는지 데이터로 판단할 수 있습니다. 더 이상 선풍기 한 대를 누구에게 드려야 할지, 기억을 더듬지 않아도 됩니다. **한정된 복지 자원이 가장 필요한 어르신에게, 가장 먼저 닿을 수 있도록.**

***

### 2.2 AI 솔루션 소개

#### 솔루션 개요

2명의 담당자가 339명의 어르신을 책임지는 현장에서, **기억이 아닌 데이터로 움직이는 사례관리**를 만들고자 했습니다. 웹 기반 통합 사례관리 플랫폼에 AI를 연동한 **'현장 밀착형 AI 사례관리 에이전트'** 가 그 답입니다. 핵심 기능은 다섯 가지입니다. **① AI 상담일지 다듬기·녹음 전사 ② 모바일 현장기록 ③ 스마트 검색 ④ 자원 배분 AI 도우미 ⑤ 사례관리 계획 추출·달성률 추적.** 그리고 이 모든 기능은 어르신의 개인정보를 지키는 장치(대상자별 AI 동의·거부, 이름 대신 고유번호 전송, 접속·열람 기록 등) 위에서 동작합니다.

**[기록의 부담을 낮추고, 데이터를 쌓습니다]**

담당자가 현장에서 간단히 메모한 내용을 '다듬기' 버튼 하나로 **복지관 평가 기준에 맞는 정제된 상담기록으로 변환**할 수 있습니다. 상담 녹음은 텍스트로 전사해 기록으로 남길 수 있고, 모바일에서도 현장 기록이 가능해 지금까지 사무실로 돌아와야만 했던 기록의 공백을 없앴습니다. 이때 AI가 작성한 내용은 바로 저장되지 않습니다. **담당자가 AI의 초안을 직접 검토하고 수정한 뒤 최종 등록하는 구조**로, 기록의 정확성과 전문적 판단은 언제나 담당자에게 있습니다. 상담을 기록하면서 **그 자리에서 제공한 물품·서비스를 제공이력으로 함께 등록**할 수 있어, 기록 한 번으로 상담과 제공 내역이 같이 쌓입니다. 기록에 쏟던 시간과 에너지가 줄어든 만큼, 지금까지 누락되어 온 어르신의 욕구와 상태가 빠짐없이 데이터로 쌓이기 시작합니다.

**[쌓인 데이터를 AI가 분석해, 판단의 근거를 만듭니다]**

축적된 상담기록은 그 자체로 자산이 됩니다. **스마트 검색 기능으로 수개월치 과거 기록을 키워드 하나로 즉시 조회**할 수 있어, 지금까지 기억에 의존하거나 기록을 일일이 뒤져야 했던 시간을 없앴습니다. 여기서 그치지 않습니다. AI는 누적된 상담 데이터를 분석해 **어르신별 욕구 변화와 긴급도를 도출**하고, 선풍기처럼 한정된 후원 자원이 들어왔을 때는 **자원 배분 AI 도우미가 상담기록과 제공이력을 함께 읽어 우선순위 대상자를 추천**합니다. 이미 제공한 물품은 다시 추천하지 않도록 걸러 내고, 종결되었거나 AI 활용을 거부한 대상자는 처음부터 제외합니다. **가장 시급한 어르신이 데이터로 보이고, 자원은 가장 필요한 곳으로 향합니다.**

담당자의 기억과 주관에 의존하던 방식에서 벗어나, **AI가 누적 데이터를 분석해 의사결정을 보조하는 현장 밀착형 사례관리.** 더 이상 가장 필요한 어르신이 가장 먼저 빠지는 일은 없어야 합니다.

> **② Supabase 프로젝트 생성 후 데이터베이스 구성**: `supabase/migrations` 폴더의 SQL을 파일명(날짜) 순서대로 SQL Editor에서 실행합니다. **가입 승인 게이트(`supabase/approval-gate`의 01→02 순서)는 반드시 설치**해야 합니다. 설치하지 않으면 가입한 계정이 승인 없이 데이터에 접근할 수 있습니다. `organizations.slug` 컬럼은 `20261007235959_add_organizations_slug.sql`이 만들어 주므로, 파일명(날짜) 순서를 지켜 실행하면 됩니다(5장 '알려진 한계' 참고).<br>
> **③ Google Gemini API 키 발급**<br>
> **④ `.env.local` 파일에 아래 항목 설정** (전체 목록은 저장소의 `.env.example` 참고)

각 항목은 데이터베이스 주소와 접근 권한 키로, **외부에 노출되면 안 되는 민감한 정보**가 포함되어 있습니다. 코드에 직접 입력하지 않고 `.env.local`(로컬) 또는 Vercel 환경변수(배포)에만 보관하며, `.env.local`은 GitHub에 업로드되지 않습니다.

```
VITE_SUPABASE_URL=                # Supabase 프로젝트 주소
VITE_SUPABASE_PUBLISHABLE_KEY=    # Supabase 공개(publishable) 키
SUPABASE_URL=                     # 서버에서 쓰는 같은 주소
SUPABASE_PUBLISHABLE_KEY=         # 서버에서 쓰는 같은 공개 키
SUPABASE_SERVICE_ROLE_KEY=        # 서버 전용 서비스 키 (절대 공개 금지)
SUPER_ADMIN_EMAILS=               # /admin 에 접근할 슈퍼 관리자 이메일(쉼표 구분, 서버 전용)
VITE_DEFAULT_WORKER_CONFIG=       # (선택) 기관별 기본 담당자 설정(JSON)
VITE_SITE_URL=                    # (선택) 내 배포 주소. 공유 미리보기(og) 태그에 사용. 비우면 https://example.com 이 표시됨
VITE_ORG_NAME=                    # 필수: 우리 기관 이름(개인정보 처리방침 등에 표시. Code.gs의 OUR_ORG_NAME과 같게)
NAVER_MAP_CLIENT_ID=              # (선택) 네이버 지도(주소 검색) 클라이언트 ID. 서버 전용
NAVER_MAP_CLIENT_SECRET=          # (선택) 네이버 지도 클라이언트 시크릿. 서버 전용, 절대 공개 금지
```

네이버 지도 키는 네이버 클라우드 플랫폼에서 직접 발급합니다. 비워 두면 지도 기능만 동작하지 않고 나머지는 정상 작동합니다.

Google Gemini API 키 등은 `.env.local`이 아니라 **Supabase Edge Function 시크릿에 별도 등록**합니다. (Supabase 대시보드 → Edge Functions → Secrets)

```
ALLOWED_ORIGINS=                 # 필수: 내 웹앱 배포 주소(쉼표 구분). 비우면 서버 함수 호출이 막힘
GEMINI_API_KEY=                   # 필수: AI 기능
GEMINI_MODEL=                     # (선택) 기본 모델. 비우면 코드의 기본값 사용
GEMINI_FALLBACK_MODELS=           # (선택) 기본 모델 실패 시 대체 모델
DRIVE_UPLOAD_URL=, DRIVE_SECRET=   # (선택) Google Drive 연동
COMPANION_SUPABASE_URL=           # (선택) 복순이(말벗 챗봇) Supabase 프로젝트 주소
COMPANION_SUPABASE_SERVICE_ROLE_KEY=  # (복순이 연동 시 필수) 복순이 프로젝트의 서버 전용 서비스 키 (절대 공개 금지). 모니터링 조회·삭제 모두 이 키로 호출
COMPANION_SUPABASE_ANON_KEY=      # (선택) 복순이 프로젝트의 공개(anon) 키. .env.example에 있으나 companion-proxy 코드는 현재 읽지 않음
COMPANION_MONITOR_SECRET=         # (복순이 연동 시 필수) 모니터 함수 비밀값. 설치자가 새로 정함
```

**복순이 연동 (선택)**: 복순이를 함께 설치하는 경우에만 위 `COMPANION_*` 값이 필요합니다. 이 중 `COMPANION_MONITOR_SECRET`은 저장소에 들어 있지 않으며 **설치하는 기관이 길고 무작위인 새 값을 직접 정해야 합니다.** 정한 값은 복순이 쪽 마이그레이션 SQL의 자리표시자(`<COMPANION_MONITOR_SECRET을_여기에_입력>`)와 이 시크릿에 **똑같이** 넣습니다(SQL 파일에 넣은 값은 커밋하지 않습니다). 설정 순서와 주의점은 [복순이 README의 '모니터링 함수 비밀값 설정'](../bright-day-talk-v2/README.md)을 따르세요. 특히 **`companion-proxy`를 먼저 배포한 뒤** `20261102000000_companion_monitor_service_role_only.sql`을 실행해야 모니터링이 끊기지 않습니다.

**Google OAuth 클라이언트 만들기**

1. Google Cloud Console → API 및 서비스 → OAuth 동의 화면을 설정합니다(앱 이름, 지원 이메일).
2. 사용자 인증 정보 → OAuth 클라이언트 ID 만들기 → 유형은 **웹 애플리케이션**을 고릅니다.
3. **승인된 리디렉션 URI**에 `https://<프로젝트 ID>.supabase.co/auth/v1/callback`을 넣습니다.
4. 발급된 `<클라이언트 ID>`와 `<클라이언트 시크릿>`을 Supabase 대시보드 → Authentication → Sign In / Providers → Google에 입력하고 켭니다. (이 값들은 저장소나 `.env` 파일에 적지 않습니다.)
5. Supabase → Authentication → URL Configuration의 Site URL과 Redirect URLs에 배포한 서비스 주소(`https://<우리 기관 주소>`)를 등록합니다.

**운영 보안 설정 (설치 후 꼭 확인)**

* **신규 가입 끄기**: 담당자 가입이 모두 끝나면 Supabase → Authentication → Sign In / Providers의 **Allow new users to sign up**을 끕니다. 가입은 누구나 신청할 수 있어 두면 관리자 승인 대기 계정이 계속 쌓일 수 있습니다. 다만 끄면 새 담당자·새 기관이 로그인할 수 없으므로, 담당자를 추가할 때만 잠시 켜서 가입시키고 승인한 뒤 다시 끄세요.
* **Gemini 예산 한도**: Google Cloud Console → 결제 → 예산 및 알림에서 월 예산과 알림(예: 50%·90%·100%)을 설정하고, API 할당량도 기관 규모에 맞게 낮춰 둡니다. 키가 유출되거나 호출이 폭증해도 요금이 한없이 늘지 않도록 하기 위함입니다.

> **⑤** Supabase Edge Function 배포: `supabase/functions` 폴더의 함수를 배포합니다. (예: `npx supabase functions deploy gemini --project-ref <프로젝트 ID>`)<br>
> **⑥ `bun install` → `bun dev` 명령으로 로컬 서버 실행**<br>
> **⑦ Vercel 등 클라우드 플랫폼에 배포하여 기관 내 서비스로 운영**

**기관에 맞게 바꿔야 하는 것**: 개인정보처리방침과 AI 활용 동의서의 기관명·연락처(개인정보 보호책임자 정보는 `src/components/PrivacyPolicyContent.tsx`), 기본 담당자 설정, 업무 매뉴얼(앱의 매뉴얼 탭에서 PDF·URL을 직접 업로드합니다. 기관 내부 문서는 저장소에 포함하지 않습니다). 또한 **기관명과 서비스 주소는 환경변수로 지정합니다**: `VITE_ORG_NAME`(기관명. 처리방침·기관 목록·삭제 보호 기관에 쓰임), `VITE_SITE_URL`(공유 미리보기 주소), Edge Function 시크릿 `ALLOWED_ORIGINS`(허용할 웹 주소). 코드에서는 `google-drive-relay/Code.gs`의 `UPLOAD_FOLDER_ID`·`OUR_ORG_NAME`(Drive 폴더와 기관명, `VITE_ORG_NAME`과 같은 이름)만 직접 바꿉니다.

**※ Supabase 무료 플랜 사용 시** 저장공간(500MB) 한계를 보완하기 위해 Google Drive와 연동하여 상담 기록 및 첨부파일을 외부에 저장할 수 있습니다. 장기 운영을 계획하는 기관의 경우 이 옵션을 활용하면 비용 부담 없이 안정적으로 운영할 수 있습니다.

단 하나의 복지관만을 위한 솔루션이 아닙니다. **전국 어느 기관이든 현장 상황에 맞게 직접 구축하고 운영할 수 있도록**, 소스코드와 설정 가이드를 함께 공개합니다.

#### 주요 기능

**해결 아이디어 1. 기록의 부담을 낮춥니다**

*관련 기능 : AI 상담일지 다듬기, 상담 녹음 전사, 모바일 현장기록, 제공이력 함께 등록*

담당자가 현장에서 간단히 메모한 내용을 '다듬기' 버튼 하나로 **복지관 평가 기준에 맞는 정제된 상담일지로 변환**합니다. 모바일에서도 현장 기록이 가능해 사무실로 돌아와야만 했던 기록의 공백을 없앴습니다. AI가 작성한 초안은 **담당자가 직접 검토·수정 후 최종 등록**하는 구조로, 판단의 주체는 언제나 담당자에게 있습니다. 결과 옆에는 **어떤 AI 모델이 만든 결과인지 표시**되어, 어떤 모델이 쓰였는지 항상 확인할 수 있습니다.

상담을 기록하는 화면에서 **'제공이력 함께 등록'** 을 체크하면, 그 자리에서 제공한 물품·서비스를 바로 입력해 상담기록과 함께 저장할 수 있습니다. 제공이력을 따로 다시 입력하는 번거로움과 누락을 줄이고, 이렇게 쌓인 제공이력은 자원 배분 추천의 정확도를 높이는 근거가 됩니다. 상담 날짜는 선택하되 시각은 화면에 표시하지 않아 기록 입력이 간단합니다.

**해결 아이디어 2. 쌓인 데이터로 자원을 공정하게 배분합니다**

*관련 기능 : 키워드 검색, 자원 배분 AI 도우미*

수개월치 상담 기록을 **키워드로 즉시 조회**할 수 있습니다. 기억에 의존하거나 기록을 일일이 뒤져야 했던 시간을 없애고, 필요한 정보를 빠르게 찾아 현장 의사결정을 즉시 지원합니다.

여기서 그치지 않습니다. *"오늘 삼계탕 30개가 들어왔는데 누구한테 나가면 좋을까?"* — 담당자가 자연어로 질문하면 **AI가 최근 12개월 상담기록·제공이력을 기반으로 우선순위 대상자를 추천**하고, 추천 이유와 **근거가 된 상담기록을 바로 열어 확인**할 수 있게 보여 줍니다. 추천 과정에는 현장에서 겪은 오류를 반영한 안전장치가 있습니다.

* **이미 제공한 물품은 다시 추천하지 않습니다.** 상담기록과 제공이력(항목·비고)에서 이미 지급한 물품을 먼저 찾아 AI에 알려 주고, 추천 결과에 같은 물품의 제공 기록이 있으면 경고와 근거를 함께 표시합니다.
* 종결된 대상자와 AI 활용을 거부한 대상자는 추천 대상에서 제외합니다.
* AI가 실제로 반영한 대상자 수를 화면에 표시해, 누락 여부를 담당자가 확인할 수 있습니다.

더 이상 한정된 자원을 누구에게 드려야 할지 기억을 더듬지 않아도 됩니다. **가장 시급한 어르신이 데이터로 보입니다.**

**해결 아이디어 3. AI가 사례관리 계획을 분석하고, 달성률을 추적합니다**

*관련 기능 : 사례관리 계획 자동 추출, 계획 대비 달성률 추적, 연간 변화 분석*

신규 대상자의 적격심사지 또는 기존 대상자의 재사정기록지를 업로드하면, **AI가 문서를 분석해 대상자별 사례관리 계획을 자동으로 추출**합니다. 담당자는 상담기록과 제공이력 등록 시 해당 내용이 어떤 계획 목표에 해당하는지 직접 연동할 수 있으며, 등록된 내용을 바탕으로 **각 어르신의 계획 대비 달성률을 한눈에 확인**할 수 있습니다.

매년 재사정 시 새로운 기록지를 업로드하면, **AI가 작년 대비 욕구 변화와 계획의 달성 여부를 자동으로 분석**해 담당자가 어르신의 변화 흐름을 빠르게 파악할 수 있습니다. 상담기록과 제공이력이 누적될수록, **계획 대비 달성률도 실시간으로 업데이트되어 지원 공백을 사전에 방지**합니다. 서비스를 종결한 대상자는 종결 사유와 함께 눈에 띄게 표시되어, 종결 여부를 놓치지 않습니다.

**해결 아이디어 4. 개인정보를 철저히 보호합니다**

*관련 기능 : 기관별 접근 제어, Google 로그인, 관리자 승인, 역할별 권한, 접속·열람 기록, AI 활용 동의·거부, 이름 대신 고유번호 전송, 정기 데이터 백업*

사례관리 데이터는 취약계층 어르신의 민감한 개인정보를 담고 있습니다. 접근, AI 전송, 기록, 보관의 네 단계로 나누어 지킵니다.

* **접근 통제** : 기관별 전용 URL과 데이터 격리로 타 기관의 데이터에는 접근 자체가 불가능합니다. **Google OAuth 인증**을 결합해 허가된 계정만 로그인할 수 있고, 신규 담당자가 가입하더라도 **관리자가 직접 승인한 이후에만 대상자 정보에 접근**할 수 있습니다. 역할은 관리자·멤버·뷰어로 나뉘며, **뷰어는 조회만 가능하며, 입력·수정은 데이터베이스에서, AI 기능은 서버 함수에서 차단**됩니다.
* **AI 전송 보호** : AI 분석에는 대상자 이름 대신 **고유번호(예: JN0001)** 를 전송하고 결과 화면에서만 이름으로 되돌립니다. 대상자마다 **AI 활용 동의 여부를 기록**하며, 거부한 대상자는 대상자와 연결된 AI 기능(분석·추천·다듬기·전사)에서 제외됩니다. 주민등록번호는 앞 7자리까지만 저장합니다.
* **기록과 감사** : **접속 이력(접속 시각·IP)** 과 **대상자 정보 열람 기록**(화면에서 연 기록 기준으로 누가 언제 어떤 대상자를 봤는지), **변경 이력**(대상자·상담·제공이력·목표)을 남기고, 관리자는 잘못된 변경을 되돌릴 수 있습니다.
* **화면 보호와 보관** : 어르신 이름을 화면에서 가리는 '이름 숨기기' 기능이 있고, 동의서 등 민감한 파일은 비공개로 두고 앱이 권한을 확인한 뒤에만 열어 줍니다. Google Drive 연동 설정 시 **주 1회 정기적으로 데이터가 자동 백업**되어, 예기치 못한 상황에서도 소중한 상담 기록이 유실되지 않도록 보호합니다.

#### AI 활용 내용

| 구분 | 내용 |
| :--------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 사용한 AI 도구·모델 | Google Gemini API (텍스트 생성·분석, 음성 전사). 기능별로 모델을 따로 설정할 수 있고, 기본 모델이 실패하면 대체 모델로 자동 전환합니다. 어떤 모델이 결과를 만들었는지 화면에 표시합니다. |

| AI를 쓰지 않은 부분 | 접근 권한, 가입 승인, 동의 기록, 접속·열람 기록, 조회·통계는 AI 없이 규칙과 데이터베이스로 처리합니다. AI는 정리되지 않은 글과 말(상담 메모·녹음·기록지)을 다루는 곳에만 사용하며, 최종 결정은 항상 담당자가 합니다. |

#### AI가 하지 않는 일 (사용 범위의 한계)

사례관리는 한 사람의 삶에 영향을 주는 업무입니다. 그래서 AI는 **초안과 참고 정보를 만드는 데까지만** 쓰고, 판단과 결정은 하지 않도록 범위를 정했습니다.

| 하지 않는 일 | 이 솔루션에서의 방식 |
| :-- | :-- |
| 서비스 대상자 선정·자격 판정 | AI가 판정하지 않습니다. 자원 배분 도우미는 후보와 근거 기록을 보여 줄 뿐이고, 누구에게 드릴지는 담당자가 정합니다. |
| 위험도·등급의 자동 부여 | 대상자의 위험도와 등급은 담당자가 입력합니다. AI 분석의 긴급도는 참고 의견이며 대상자 정보에 자동으로 반영되지 않습니다. 복순이 모니터링의 위험 표시는 AI가 아니라 키워드 규칙이고, 담당자가 확인 처리합니다. |
| 기록의 자동 저장·수정 | 상담 초안은 담당자가 확인하고 저장해야만 저장됩니다. AI가 상담기록·제공이력·대상자 정보를 자동으로 쓰거나 바꾸지 않습니다. AI 서버 기능이 저장하는 것은 담당자가 요청한 분석 리포트뿐입니다. |
| 서비스 중단·종결의 결정 | AI는 관여하지 않습니다. 종결 처리와 종결보고는 담당자가 직접 하며, 첨부 문서 분석은 입력을 돕는 보조 기능이라 담당자가 확인한 뒤 저장합니다. |
| AI 활용을 거부한 대상자의 정보 사용 | 대상자별로 거부하면 AI 분석·추천·다듬기·전사에서 제외됩니다. |

AI는 틀릴 수 있습니다. 그래서 AI 결과에는 사용한 모델을 표시하고, 자원 배분 추천과 매뉴얼 답변에는 근거(참고한 상담기록·페이지)도 함께 보여 주며, 오류가 나도 담당자가 입력한 원본은 보존합니다. 실제로 "이미 제공한 물품을 다시 추천하는" 오류를 현장에서 발견해 규칙으로 보완한 것처럼, 사용하면서 발견한 오류는 기록하고 고쳐 나갑니다. 사고에 대비한 대응 절차는 [침해사고 대응 절차](./docs/incident-response.md)에 정리했습니다.

**AI 성능 개선 시도**

좋은 아이디어도 실제 현장에서 작동하지 않으면 의미가 없습니다. 개발 과정에서 마주친 문제들을 하나씩 해결하며 현장에서 바로 쓸 수 있는 수준으로 다듬었습니다.

**① 상담일지 품질 문제 — 현장 양식을 AI에게 가르쳤습니다**<br>
처음에는 메모를 그대로 AI에게 전달했더니 너무 일반적인 문장만 생성됐습니다. 복지관에서 실제로 사용하는 상담일지의 항목 구조(날짜·대상자·상담 내용·욕구·향후 계획)를 AI에게 미리 정의해 줬습니다. **그 결과 현장에서 바로 사용할 수 있는 수준의 상담일지가 생성**되기 시작했습니다.

**② 동명이인 혼동 문제 — 어르신마다 고유 번호를 부여했습니다**<br>
AI가 이름만으로 어르신을 구별하다 보니, 같은 이름의 어르신 기록을 혼동하는 오류가 발생했습니다. 모든 대상자에게 **고유번호**를 부여하고 AI에는 이름 대신 번호를 전달하는 방식으로 바꿨고, **이후 혼동 오류가 사라졌습니다.** 이 방식은 AI에 어르신 이름이 직접 전달되지 않는다는 점에서 개인정보 보호에도 도움이 됩니다.

**③ AI 오류 시 기록 유실 문제 — 원본은 반드시 보존합니다**<br>
AI 응답이 실패하거나 지연될 경우, 담당자가 입력한 원본 메모가 사라질 수 있는 위험이 있었습니다. AI 오류가 발생하더라도 **담당자가 입력한 원본 메모는 반드시 저장되도록** 안전장치를 마련했습니다. 기록 자체가 유실되는 상황을 원천 차단했습니다.

**④ 이미 준 물품을 다시 추천하는 문제 — AI에게만 맡기지 않고 규칙으로 막았습니다**<br>
실제 사용 중에, 상담기록에 "이불을 이미 배분했다"고 적혀 있는데도 자원 배분 AI가 같은 어르신에게 이불을 다시 추천하는 일이 있었습니다. AI의 판단에만 맡기지 않고, **코드가 상담기록과 제공이력에서 이미 제공한 물품을 먼저 찾아 AI에게 알려 주고, 추천 뒤에도 같은 물품의 제공 기록이 있으면 경고**하도록 보완했습니다. 근본 원인인 제공이력 누락을 줄이기 위해, **상담을 기록하면서 제공이력을 함께 등록하는 기능**도 추가했습니다.

### 2.3 이용자용 가이드

**이용 전 준비사항**

별도 프로그램 설치는 필요하지 않습니다. 크롬 등 웹 브라우저와 Google 계정만 있으면 됩니다. 처음 가입하면 **관리자의 승인**을 받아야 하며, 승인되기 전에는 대상자 정보에 접근할 수 없습니다.

스마트폰에서는 브라우저 메뉴의 **'홈 화면에 추가'** 를 선택하면 앱처럼 바로 실행할 수 있습니다. iOS와 Android 모두 지원되며, 현장에서 더욱 편리하게 사용할 수 있습니다.

**실제 이용 방법**

1. 웹 브라우저에서 기관 전용 URL에 접속합니다. (`https://서비스주소/기관별_부여주소` 형태)
2. Google 계정으로 회원가입 후 관리자 승인을 기다립니다.
3. 승인 완료 후 Google 계정으로 로그인합니다.
4. 대시보드에서 담당 대상자를 추가하거나 목록을 확인합니다. (신규 기관의 경우 대상자 등록 후 사용)
5. 상담 기록을 남길 때는 어르신 이름을 클릭 → 상담 탭 → 상담 날짜와 방식을 선택한 후, 현장 메모를 짧게 입력합니다. (예: '파스 필요, 허리 다침, 식사 거름') 상담을 녹음하면 텍스트로 전사해 줍니다.
6. **AI 다듬기** 버튼을 누르면 표준 상담일지 형식으로 문장이 정리됩니다. 어떤 모델이 만든 결과인지 옆에 표시됩니다.
7. 내용을 확인한 후 저장합니다. 내용이 어색하면 **AI 다듬기**를 다시 실행하거나 [되돌리기]로 원문을 복원할 수 있고, 직접 수정해도 됩니다.
8. 그 자리에서 물품이나 서비스를 제공했다면 **'제공이력 함께 등록'** 을 체크하고 항목·수량·제공기관을 입력합니다. 상담을 저장할 때 제공이력도 함께 등록됩니다. (구체적인 물품명은 항목이나 비고에 적어 주세요. 자원 배분 도우미가 이미 제공한 물품을 가려내는 데 쓰입니다.)
9. 신규 대상자의 적격심사지 또는 기존 대상자의 재사정기록지를 업로드하면, **AI가 사례관리 계획을 자동으로 추출**합니다. 상담기록과 제공이력 등록 시 해당 목표에 연동하면 **계획 대비 달성률을 한눈에 확인**할 수 있습니다.
10. 매년 재사정 시 새로운 기록지를 업로드하면 **AI가 작년 대비 욕구 변화와 달성 여부를 자동으로 분석**해 어르신의 변화 흐름을 빠르게 파악할 수 있습니다.
11. 축적된 상담 기록은 **키워드로 즉시 검색**할 수 있습니다. 필요한 정보를 빠르게 찾아 현장 의사결정을 즉시 지원합니다.
12. 한정된 후원 자원이 들어왔을 때는 **자원 배분 AI 도우미**에 자연어로 질문하세요. (예: *"오늘 삼계탕 30개가 들어왔는데 누구한테 나가면 좋을까?"*) AI가 최근 12개월 상담·제공이력을 기반으로 **우선순위 대상자를 추천**하고, 근거가 된 상담기록을 바로 볼 수 있습니다. 이미 제공한 물품이면 경고가 표시됩니다.
13. 달력 화면에서는 공휴일·절기와 함께 상담·제공 일정을 월별로 확인할 수 있고, 이름을 누르면 그 어르신의 기록만 따로 볼 수 있습니다.
14. 어르신 이름이 화면에 보이면 곤란한 자리(회의, 시연 등)에서는 상단의 **이름 숨기기**를 켜세요.

**이용 시 주의사항**

* AI가 생성한 문장은 반드시 검토 후 저장하세요. AI가 사실과 다른 내용을 추가하는 경우 담당자가 직접 수정해야 합니다.
* 상담 날짜는 실제 상담이 이루어진 날로 정확히 입력해 주세요. 추후 욕구 분석 데이터의 기준이 됩니다. (시각은 기록하지 않습니다.)
* 어르신의 민감한 개인정보(의료 정보, 가족 갈등 등)는 꼭 필요한 범위 내에서만 기록합니다.
* AI는 어르신 이름 대신 고유번호를 받지만, **상담 내용 속에 적은 이름은 그대로 전달**될 수 있습니다. 본문에는 불필요한 실명을 적지 않는 것을 권장합니다.
* AI 활용을 원하지 않는 어르신은 대상자 정보에서 'AI 활용 거부'로 설정하면, 대상자와 연결된 AI 기능(분석·추천·다듬기·전사)에서 제외됩니다. 단, 대상자를 등록하기 전에 문서를 올려 분석하는 기능처럼 대상자가 아직 정해지지 않은 단계에는 적용되지 않으므로, 이 경우 문서에 거부 대상자 정보가 포함되지 않았는지 담당자가 확인해야 합니다.

#### 관리자(슈퍼바이저)용

**담당자 승인 및 역할 관리**

신규 기관의 경우, **첫 번째 가입자가 자동으로 관리자**가 됩니다. 이후 담당자가 Google 계정으로 가입하면 관리자 화면에 **'가입 승인 대기'** 로 표시되고, 관리자가 승인해야 대상자 정보에 접근할 수 있습니다.

역할은 세 가지로 구분됩니다.

* **관리자** : 가입 승인·역할 변경·멤버 내보내기·기관 설정·접속/열람 기록 확인 등 전체 권한
* **멤버** : 대상자 상담기록 조회 및 등록 등 실무 권한
* **뷰어** : 데이터 조회만 가능, 수정·AI 기능 사용 불가 (데이터베이스에서 차단)

승인 방법은 아래와 같습니다.

1. 관리자 계정으로 로그인 후 '기관 멤버' 메뉴 접속
2. '가입 승인 대기' 목록에서 본인 확인 후 승인
3. 필요하면 역할(관리자·멤버·뷰어)을 변경
4. 승인된 계정은 즉시 사용 가능

**Google Drive 백업 설정 방법**

1. IT 담당자가 `google-drive-relay/Code.gs`를 Google Apps Script에 배포합니다 (최초 1회 서버 설정). 스크립트 속성에 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`(필요하면 `BACKUP_NOTIFY_EMAIL`)를 등록하고, 업로드 폴더 ID(`UPLOAD_FOLDER_ID`)를 자기 기관 폴더로 바꿉니다.
2. Apps Script에서 `setupMondayBackupTrigger`(주 1회) 또는 `setupDailyBackupTrigger`(매일) 함수를 **한 번 실행**해 자동 실행을 등록합니다.
3. 등록하면 **상담기록, 제공이력, AI 리포트 등 주요 데이터가 자동으로 Google Drive에 백업**되고, 문제가 있으면 폴더 이름 끝에 `_INCOMPLETE`가 붙습니다.
4. 백업된 파일은 연동된 Google Drive 폴더에서 확인할 수 있습니다. (테이블 구조 외의 DB 설정은 백업되지 않으므로 `supabase/migrations`와 함께 보관하세요.)

**운영 중 신경 써야 할 사항**

* **담당자 계정 관리** : 퇴사하거나 담당이 변경된 경우, 기관 멤버 화면에서 해당 계정을 **즉시 내보내기** 해야 합니다. 그대로 두면 퇴사자가 어르신의 개인정보에 접근할 수 있습니다.
* **접속·열람 기록 확인** : 관리자 화면에서 접속 이력(IP 포함), 대상자 열람 기록, 변경 이력을 기간·직원별로 조회할 수 있습니다. 이상한 접근이 보이면 해당 계정을 바로 내보내세요.
* **Gemini API 사용량** : Google Cloud Console에서 월별 API 호출량을 주기적으로 확인합니다. 한도 초과 시 AI 기능이 일시 중단될 수 있으므로 사용 요금제를 확인해 두세요.
* **Supabase 플랜** : 무료 플랜은 일정 기간 비활성 시 프로젝트가 일시 정지되어 **서비스 전체가 중단**될 수 있습니다. 장기 운영 시 반드시 유료 플랜으로 전환하거나 Google Drive 백업을 설정하세요.

**운영 전 준비사항**

* 운영 계정(Google, Supabase, Vercel, GitHub)에는 **2단계 인증을 적용**하는 것을 권장합니다.

**운영 방법**

코드를 수정한 뒤 GitHub 저장소에 push하면 Vercel이 자동으로 감지하여 재배포합니다. 별도의 서버 재시작이나 수동 배포 작업은 필요하지 않습니다. 데이터베이스 변경이 필요한 경우 `supabase/migrations`에 추가된 SQL을 Supabase 대시보드의 SQL 에디터에서 실행합니다. Edge Function은 `npx supabase functions deploy <함수명> --project-ref <프로젝트 ID>`로 배포합니다.

**운영 중 신경 써야 할 사항**

* **모델 버전 확인** : Gemini 모델은 정기적으로 변경될 수 있습니다. **코드 수정 없이** Supabase Edge Function 시크릿의 `GEMINI_MODEL`, `GEMINI_FALLBACK_MODELS` 값만 바꾸면 모델을 교체할 수 있고, 화면의 AI 모델 표시로 실제로 어떤 모델이 쓰이는지 확인할 수 있습니다. (오류가 나면 모델 퇴역 여부를 먼저 확인하세요.)
* **의존 라이브러리 점검** : 보안 패치가 나오는 경우가 있으므로 정기적으로 의존성을 점검하고 업데이트하세요.

### 3.1 현장 적용 결과

**업무 방식의 변화**

기존에는 담당자가 현장 방문 후 돌아와 기억을 되살려 상담일지를 작성하거나, 시간이 부족할 경우 기록을 생략하는 일이 빈번했습니다. 솔루션 도입 이후 현장에서 단문 메모만 입력해도 AI가 표준 양식의 상담일지를 자동 생성하여, 기록에 소요되는 시간이 크게 단축되었습니다. 특히 **PWA(Progressive Web App) 기술을 적용하여 별도 앱 설치 없이 스마트폰 홈 화면에 아이콘을 추가하는 것만으로 앱처럼 실행**할 수 있습니다. iOS와 Android 모두 지원되며, 담당자가 어르신 댁을 방문한 자리에서 바로 상담 내용을 기록할 수 있어 **현장 기록 누락을 원천적으로 줄이는 환경**이 만들어졌습니다. 담당자는 *"상담기록, 수정, 출력과 같은 전반적인 프로세스가 간소화됐어요"* 라고 피드백했습니다.

도입 전 기존 시스템에서 상담기록 1건 작성 시 **10분 이상 소요가 56.5%**, 20분 이상 소요도 39.1%로 기록 부담이 높았습니다. 또한 하루 상담기록 작성·관리 시간이 **10분 이상 단축될 것이라는 기대가 56.7%**, 5분 이상 단축 기대도 76.7%로 나타났습니다.

### 3.2 시행착오와 개선

**① AI가 목표달성률을 잘못 산출하는 할루시네이션 문제 — 담당자 판단 구조로 전환**

초기에는 AI가 상담기록과 제공이력을 자동으로 분석해 사례관리 계획의 대상자별 목표달성률을 산출하도록 설계했습니다. 하지만 실제로 적용해보니 AI가 상담 내용과 계획 목표 간의 연관성을 잘못 판단하는 경우가 많아 **부정확한 정보가 반복적으로 생성**됐습니다. 복지 현장에서 잘못된 달성률은 단순한 오류가 아니라 잘못된 자원 배분으로 이어질 수 있어 반드시 해결해야 했습니다.

여러 방식을 검토한 끝에, **AI에 전적으로 의존하는 방식 대신 담당자가 판단하는 구조**로 전환했습니다. 상담기록과 제공이력을 작성할 때 해당 내용이 사례관리 계획의 어떤 목표에 해당하는지 담당자가 직접 연동 여부를 판단해 등록하고, 등록된 내용을 바탕으로 **목표달성률을 한눈에 확인할 수 있도록** 했습니다. AI가 모든 것을 자동화하는 것보다, 담당자의 전문적 판단이 더 정확한 데이터를 만든다는 것을 현장에서 직접 확인한 중요한 교훈이었습니다.

**② 데이터가 쌓일수록 느려지는 구조 문제 — 전용 테이블로 분리**

초기에는 상담 기록과 서비스 계획 연동 데이터를 `clients.note` 컬럼에 JSON 문자열로 저장하는 방식을 사용했습니다. 하지만 데이터가 쌓일수록 시스템에 부담이 커져 속도가 느려질 수 있다는 한계가 확인됐고, 전용 테이블(`care_plan_action_links`)로 분리하는 작업이 필요했습니다.

이를 위해 새 데이터를 기존 방식과 신규 테이블에 **동시에 기록하는 이중쓰기(Dual-Write) 전략**을 단계적으로 설계했습니다. 신규 테이블에 쓰기를 추가하고, 읽기를 신규 테이블 우선으로 전환하며, 오류가 없는 것을 확인한 뒤 구버전 읽기를 제거하는 순서입니다. 이 과정에서 연동 해제 시 상태가 초기화되지 않는 문제, 배열 재할당 버그 등을 추가로 발견하고 수정했습니다. **서비스 안정성을 최우선으로 하되, 데이터 무결성을 유지하며 전환하는 구조를 직접 설계한 경험**이었습니다. 현재 신규 테이블로 읽기 전환까지 마쳤고, 기존 `note` 데이터의 정리는 백업을 확인하며 단계적으로 진행하고 있습니다.

**③ 현장에서 발견한 AI 추천의 빈틈 — 규칙과 입력 구조로 보완**

자원 배분 AI를 실제로 써 보니, 이미 이불을 배분했다고 상담기록에 적혀 있는데도 같은 어르신에게 이불을 다시 추천하는 경우가 있었습니다. 종결된 대상자가 추천 목록에 섞이는 문제도 발견됐습니다. AI의 성능을 더 높이는 데서 멈추지 않고, **코드가 이미 제공한 물품을 먼저 찾아 알려 주고 추천 뒤에도 다시 검증**하도록 했으며, 종결·AI 거부 대상자는 처음부터 제외했습니다. 근본 원인이 제공이력 누락이라고 보고, **상담을 기록하면서 제공이력을 함께 등록**하게 해 입력 단계에서부터 데이터가 쌓이도록 개선했습니다. 이 밖에 달력에서 한 어르신만 보고 싶어도 그날 전체가 펼쳐지던 불편처럼, 현장 피드백이 곧바로 화면 개선으로 이어졌습니다.

**④ 개인정보와 AI 활용의 균형 — 이름 대신 번호, 거부할 권리**

AI 분석의 정확도를 높이려면 상담 내용을 전달해야 하지만, 어르신의 개인정보를 그대로 보낼 수는 없었습니다. 이름 대신 **고유번호를 전송**하고, 대상자마다 **AI 활용 동의·거부를 기록**해 거부한 어르신은 대상자와 연결된 AI 기능에서 제외하도록 했습니다. 또한 누가 언제 어떤 어르신의 정보를 열람했는지 남기는 **열람 기록과 접속 기록**을 추가해, 문제가 생겼을 때 확인할 수 있는 근거를 마련했습니다.

**⑤ 남아있는 한계**

AI가 생성하는 상담일지가 복지관 고유의 전문 용어와 문체를 완벽히 반영하지 못하는 경우가 있어 담당자의 수정이 여전히 필요합니다. 절기 및 설날 날짜 데이터는 현재 2028년까지만 하드코딩되어 있어 매년 업데이트가 필요하며, 긴급도 기반 자원 배분 기능은 현재 구현되어 있으나 **정확도 모니터링을 통한 지속적인 업그레이드가 필요**합니다. 또한 고유번호 방식은 이름을 직접 보내지 않는 보조 장치일 뿐 완전한 비식별 처리는 아니며, **상담 본문 속에 적힌 이름까지 가리지는 못합니다.** 이 부분은 앞으로 보완할 과제로 남겨 두었습니다.

기능적 한계 외에도, **솔루션을 3주간 실제 현장에서 가동한 결과, 매주 새로운 피드백과 수정 사항이 발생**했습니다. 현장의 업무 방식과 용어는 기관마다, 담당자마다 다르기 때문에 일회성 개발로 완성되는 솔루션이 아닙니다. **지속적인 현장 모니터링과 버전업이 반드시 필요**하며, 이를 위한 운영 체계를 함께 갖추는 것이 앞으로의 과제입니다.

### 3.3 향후 계획 및 임팩트 확산

**단기 계획 (2026년 내)**

서비스 제공 계획과 실제 제공 기록을 연동하는 기능을 안정화하여, 계획 대비 이행률을 실시간으로 추적하는 체계를 완성합니다. AI가 누적 상담 기록을 분석하여 어르신별 긴급도와 욕구 충족도를 시각화하는 대시보드를 고도화하고, 한정된 후원 자원이 들어왔을 때 가장 시급한 대상자를 추천하는 자원 배분 기능의 정확도를 **현장 사용 결과를 모니터링하며 계속 높여 갑니다.** 또한 상담 본문 속 이름 처리 등 개인정보 보호 수준을 한 단계 더 높이는 작업을 이어 갑니다.

**중기 계획 (2027년)**

현재 시립중랑노인종합복지관 단독 운영에서 중랑구 내 유관기관으로 확산을 추진합니다. 기관별 전용 URL과 접근 권한 구조가 이미 갖추어져 있어, **신규 기관 추가 시 별도 개발 없이 즉시 적용이 가능합니다.** 사례관리 담당자 간 대상자 인수인계 기능과 기관 간 연계 서비스 현황 공유 기능도 추가할 계획입니다.

이러한 확산 가능성은 자체 설문 결과에서도 확인되었습니다. 설문에 참여한 30명은 시립중랑노인종합복지관뿐 아니라 대청종합사회복지관, 시흥시노인종합복지관, 경기도시각장애인복지관 등 여러 지역의 실무자로 구성되었으며, 이들 역시 상담 데이터 누락, 기록 관리의 어려움 등 유사한 현장 문제를 경험하고 있었습니다. 이는 본 솔루션이 특정 기관에만 필요한 시스템이 아니라, 유사한 사례관리 업무 구조를 가진 지역사회 복지기관에 확산·적용할 수 있는 가능성이 있음을 보여줍니다.

**장기 비전**

고령화 사회에서 사례관리 담당자 1인이 감당해야 하는 대상자 수는 계속 증가하고 있습니다. 본 솔루션이 지향하는 것은 AI가 담당자를 대체하는 것이 아니라, AI가 행정 부담을 줄여 담당자가 사람을 더 잘 만날 수 있게 하는 것입니다.

나아가 누적된 어르신별 상담 데이터를 기반으로, **어르신 개인 맞춤형 AI 챗봇(복순이)과 연동하는 쌍방향 모니터링 체계**를 구축하고자 합니다. 담당자가 어르신을 모니터링하는 것을 넘어, 어르신이 직접 챗봇을 통해 자신의 상태와 필요를 전달할 수 있는 구조입니다. 기록의 부재로 사각지대에 놓이는 어르신이 없도록, **전국 지역사회 복지관으로 확산 가능한 표준 모델**을 만들어 나가겠습니다.

### 4.5 개인정보·AI 윤리 항목

1. 어떤 개인정보를 모으고, 어디에 쓰고, 어디로 보내는지 설명해 주세요. (예: 이름·연락처·이용 기록 등 수집 항목, AI 모델·외부 API로 전송하는 경우 포함)

   사례관리 업무 수행을 위해 대상자의 **이름·연락처·생년월일·주소·가족관계·상담 내용·욕구 정보·서비스 제공 기록**을 수집합니다. 주민등록번호는 **앞 7자리까지만** 저장합니다. 수집된 정보는 담당자의 **사례관리 업무 지원과 AI 기반 욕구 분석·자원 매칭**에 활용됩니다. 데이터는 **Supabase(클라우드 데이터베이스)에 저장**되며, 저장소 기본 암호화와 전송 구간 암호화(HTTPS)가 적용됩니다. AI 기능에는 **대상자 이름 대신 고유번호를 전송**하며(상담 내용 속에 적힌 이름은 그대로 포함될 수 있습니다), AI 다듬기는 담당자가 입력한 메모 텍스트만 전송합니다. 적격심사지·재사정기록지 같은 **문서를 분석하는 기능은 문서 원문이 전송**됩니다(문서에 적힌 이름 포함). **AI 활용에 동의하지 않았거나 거부한 대상자(동의 전 미설정 포함)의 정보는 대상자와 연결된 AI 기능에 전송하지 않습니다.** AI 처리를 위해 전송된 데이터는 Google Gemini API 서버에서 처리되며(국외 서버를 거칠 수 있음), 이 사실은 개인정보처리방침에 안내하고 있습니다. **Gemini API는 결제(유료) 등급 키일 때만 전송된 데이터가 모델 학습에 쓰이지 않는 것으로 안내되며, 무료 등급이면 입력이 제품 개선·학습에 쓰일 수 있습니다. 키 등급은 운영 기관이 확인해야 합니다.** 또한 분석 결과는 기관 담당자만 접근 가능한 환경에서만 활용되며, 외부에 공개되거나 제3자에게 제공되지 않습니다.

2. 개인정보를 수집·활용했다면, 이용자의 동의를 받았는지 또는 동의 없이 써도 되는 근거가 무엇인지 설명해 주세요. (예: 회원가입 시 동의 받음/ 별도 동의 없이 공개된 정보만 사용함 등)

   대상자의 개인정보는 기관(시립중랑노인종합복지관)의 복지 서비스 제공 목적 내에서, **기존 사례관리 등록 절차에 따라 대상자 본인의 동의를 받아 수집된 정보를 활용**합니다. 본 솔루션은 기존에 동의된 정보를 기록·관리하는 업무 도구로, **새로운 개인정보를 별도로 추가 수집하지 않습니다.** AI 분석 기능 도입에 따라 **개인정보처리방침을 개정해 서비스에 반영했고, 대상자별 'AI 활용 동의서'(전자 서명·열람, 동의 이력 기록)와 동의·거부 설정 기능을 갖추었습니다.** 동의서 문구는 기관 내부 검토를 진행하며 보완하고 있습니다.

3. 개인정보를 어떻게 처리하는지, 그리고 AI를 사용한다는 사실을 이용자에게 어떻게 알리는지 설명해 주세요. (예: 서비스 화면에 "AI가 생성한 답변입니다" 표시, 개인정보처리방침 페이지 등)

   수집된 개인정보는 **Supabase PostgreSQL에 저장**(저장소 기본 암호화, 전송 구간 HTTPS)되며, **기관별 데이터 격리와 가입 승인, 역할별 권한(관리자·멤버·뷰어)으로 허가된 담당자만 열람**할 수 있습니다. 누가 언제 어떤 대상자의 정보를 열람했는지 **열람 기록과 접속 기록(IP 포함)** 을 남기고(화면에서 연 기록 기준), 대상자·상담·제공이력·목표의 변경 이력을 관리자가 확인·되돌릴 수 있습니다. AI가 생성한 상담일지는 **자동 생성된 내용임을 담당자가 인지할 수 있도록 구분 표시**되며, **어떤 AI 모델이 만든 결과인지도 화면에 표시**됩니다. 저장 전에는 반드시 담당자의 확인을 거치도록 설계되어 있고, 서비스 내 **개인정보처리방침 페이지를 별도로 제공**하며 AI 활용 사실과 전송 범위를 안내합니다.

4. AI가 틀리거나 부적절한 답을 했을 때, 사람이 확인하고 고칠 수 있는 절차가 있는지 설명해 주세요. (예: 관리자 검수 화면, 신고 기능, 응답 로그 모니터링 등)

   AI가 생성한 상담일지는 **자동 저장되지 않습니다.** 담당자가 내용을 직접 검토한 후 저장 버튼을 눌러야만 저장되며, 저장 이후에도 **수정 버튼을 통해 언제든지 내용을 변경**할 수 있습니다. AI 다듬기 기능 역시 결과를 즉시 반영하지 않고 **[되돌리기]로 원문을 복원할 수 있으며, 담당자의 최종 확인을 거칩니다.** 자원 배분 추천은 **근거가 된 상담기록을 바로 열어 확인**할 수 있고, 이미 제공한 물품이면 경고가 표시됩니다. 대상자·상담·제공이력·목표의 변경은 **변경 이력으로 남아 관리자가 확인하고 되돌릴 수 있습니다.** 모든 AI 출력물은 **담당자의 검토·수정·승인을 거치는 구조로, AI가 단독으로 최종 기록을 확정하는 경우는 없습니다.**

5. AI 사용으로 이용자가 실제로 피해를 볼 수 있는 상황을 어떻게 막고 있는지 설명해 주세요. (예: 잘못된 의료·법률 정보 제공 방지, 생성형AI서비스 학습데이터로 사용되지 않도록 설정 등)

   AI는 **상담 기록 작성, 욕구 분석, 계획 추출, 자원 배분 추천 등 보조 역할**을 하며, 서비스 제공 여부나 자원 배분의 **최종 결정은 반드시 담당자가 내립니다.** AI가 생성한 긴급도 우선순위와 욕구 분석 결과는 **의사결정 참고 자료로만 제공**되고, AI의 판단이 곧 결정으로 이어지는 구조를 배제했습니다. 자원 배분에서는 **이미 제공한 물품을 다시 추천하지 않도록 규칙으로 한 번 더 검증**하고, 종결 대상자와 AI 활용 거부 대상자를 제외합니다. 또한 **Gemini API 호출이 실패하거나 응답이 비어 있는 경우 원본 메모를 덮어쓰지 않고 오류를 안내하여 담당자가 직접 저장하도록 설계**되어 있습니다. **Gemini API 키가 결제(유료) 등급일 때만 전송된 데이터가 모델 학습에 사용되지 않는 것으로 안내되며(키 등급은 운영 기관이 확인), 대상자 정보는 이름 대신 고유번호로 전송**해 개인정보 노출 위험을 줄였습니다. 다만 상담 본문과 업로드 문서 속 이름까지 가리지는 못하는 점은 알려진 한계입니다.

### 알려진 한계

솔직하게 공개합니다. 도입 전에 확인해 주세요.

* **AI 전송 범위**: 이름 대신 고유번호로 보내는 것은 대상자의 구조화된 정보에 한정됩니다. 상담 본문과 업로드한 문서(적격심사지·재사정기록지 등) 속에 적힌 이름은 그대로 전송될 수 있습니다. AI 활용 동의 확인(동의한 대상자만 사용)은 화면이 대상자를 지정해 요청하는 경로에서 동작하는 방식입니다. 서버의 `gemini` 함수는 가입 승인된 기관 멤버만 호출할 수 있지만, 승인된 멤버가 임의의 내용을 보내는 것까지 막지는 않습니다.
* **기록의 범위**: 변경 이력은 대상자·상담·제공이력·목표에 대해서만 남고, 열람 기록은 화면에서 연 행동을 기준으로 합니다(엑셀 내보내기 등은 기록되지 않습니다). 접속·열람 기록은 브라우저가 저장하는 값이라 정교한 위조까지 막지는 못합니다.
* **설치 재현성**: 빈 Supabase 프로젝트에 `supabase/migrations`를 파일명(날짜) 순서대로 적용하는 시험에서, `organizations.slug` 컬럼을 만드는 SQL이 저장소에 없어 `20261008000000`에서 멈췄습니다. 그래서 이 컬럼을 만드는 `20261007235959_add_organizations_slug.sql`을 추가했습니다. 컬럼을 먼저 만들어 둔 상태에서는 마이그레이션 전체가 오류 없이 적용됐습니다. 추가한 파일만으로 빈 데이터베이스에 처음부터 다시 적용하는 시험은 아직 하지 않았습니다. 앱을 띄워 보는 시험도 하지 않았으므로 실제 Supabase 프로젝트에서의 전체 동작은 설치 기관이 확인해야 합니다.
* **기관 간 분리**: 복순이 위험 알림의 '확인' 기록(`companion_ack`)은 `org_id`로 기관별로 분리됩니다(마이그레이션 `20261102000000_companion_ack_org_isolation.sql` 적용 필요). 적용 전 DB에서는 기관 구분 없이 공유되므로 먼저 적용하세요.
* **파일 읽기 범위**: `drive-proxy`의 `getFileText`는 가입 승인된 기관 멤버만 쓸 수 있지만, 파일 ID를 호출하는 쪽이 정하므로 승인된 멤버는 같은 Drive 계정 안의 다른 파일 ID도 요청할 수 있습니다. 여러 기관이 한 Drive를 함께 쓰는 운영은 권장하지 않으며, 운영 시에는 신규 가입 승인을 신중히 하고 단일 기관 전용으로 운영하세요.
* **파일 공유**: 가계도 그림, PDF 원본(재사정·종결보고 등)은 링크를 아는 사람이 열 수 있는 상태로 Drive에 저장됩니다. 상담 녹음·동의서·전사·추출 텍스트는 비공개이며, 동의서와 텍스트는 앱이 권한을 확인한 뒤에만 열어 줍니다. 이미 올라간 상담 녹음은 Apps Script에서 `lockSensitiveFiles`를 실행해야 비공개로 바뀝니다.
* **의존성 점검**: 빌드·개발 도구를 중심으로 알려진 취약점이 보고된 라이브러리가 남아 있습니다(배포된 서비스에는 포함되지 않는 것이 대부분이며, 엑셀 라이브러리는 npm 배포본으로는 수정 버전이 없습니다). 정기적인 점검과 업데이트가 필요합니다.
