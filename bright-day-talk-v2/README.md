# 복순이 — 어르신 AI 말벗 챗봇

사례관리 대시보드에 쌓인 기록을 바탕으로 어르신과 매일 안부를 나누고, **혼자 계신 어르신의 위기 신호가 담당 복지사에게 닿도록** 돕는 AI 말벗 챗봇

## 1. 팀 기본 정보

### 1.1 기관 정보

시립중랑노인종합복지관은 ‘덕불고필유린의 정신으로 모두가 은혜로운 하나의 세상을 만든다’는 미션 아래 지역사회 어르신들이 존엄한 노후를 보내실 수 있도록 힘쓰고 있습니다. 우리 기관은 평생교육과 취약계층 지원을 넘어, 의료·복지·마을이 연계된 민관협력 중심의 '돌봄통합지원'을 적극 추진하며 어르신들이 살던 곳에서 건강한 노후를 보낼 수 있도록 돕고 있습니다. 사별 어르신의 정서적 자립 프로그램인 ‘도란도란’, 아동성폭력예방을 위한 노인 봉사단 ‘빨간망토 인형극단’ 등 주체적인 사회 참여를 이끄는 특화 사업을 통해 세대가 상생하는 복지 공동체를 선도하고 있습니다.

## 2. AI 솔루션

### 2.1 문제 정의

시립중랑노인종합복지관 사례관리 담당자는 단 2명입니다. 이 두 사람이 사례관리 20명, 밑반찬 40명, 무료급식 286명, **총 339명의 취약계층 어르신을 전담**합니다. 어르신 한 분 한 분의 안부를 날마다 확인하고 싶어도, 전화와 방문은 시간이 정해져 있고 담당자의 하루는 한정돼 있습니다.

**[현장의 현실 : 안부 확인과 안부 확인 사이에는 공백이 있습니다]**

혼자 사시는 어르신에게 담당자의 전화와 방문은 소중한 접점이지만, 그 사이의 며칠은 아무도 모르는 시간입니다. 몸이 불편해졌는지, 식사는 잘 하시는지, 마음이 가라앉아 있는지는 다음 연락 때에야 알게 됩니다. 어르신에게는 하루 종일 한마디도 나눌 사람이 없는 날도 있습니다.

사례관리 기록은 담당자가 어르신을 위해 쌓아 온 가장 소중한 자산인데, 지금은 **담당자만 읽는 기록**에 머물러 있습니다. 어르신은 그 기록 덕분에 달라지는 것을 느끼지 못하고, 담당자도 어르신이 오늘 어떻게 지내시는지는 기록이 아니라 다음 방문에서야 알게 됩니다.

**[솔루션 : 담당자가 아는 어르신을 이해하는 말벗이, 매일 안부를 나눕니다]**

복순이는 사례관리 대시보드에 쌓인 어르신별 기록(최근 상담, 주요 욕구, 목표, 제공받은 서비스)을 읽기 전용으로 가져와, **어르신을 이미 알고 있는 말벗**으로 대화합니다. "지난번에 허리가 아프다고 하셨는데 요즘은 어떠세요?"처럼 기록에서 화제를 찾아 안부를 묻고, 어르신이 건강이나 마음의 어려움을 말씀하시면 담당자가 모니터링 화면에서 대화와 AI 분석 결과를 확인할 수 있습니다. 위급한 말씀이 나오면 119와 1393 같은 도움받을 곳을 가장 먼저 안내합니다.

담당자가 어르신을 일방적으로 살피던 구조에서, **어르신이 직접 말을 걸고 담당자가 그 이야기를 이어받는 쌍방향 돌봄**으로 넘어가는 것이 복순이가 지향하는 방향입니다.

***

### 2.2 AI 솔루션 소개

#### 솔루션 개요

복순이는 **글자를 읽고 쓰는 것이 불편한 어르신도 말로 이야기할 수 있는 AI 말벗**입니다. 어르신은 고유번호 4자리와 생년월일 6자리로 접속하고, 말하거나 글자로 적으면 복순이가 말과 글로 답합니다. 사례관리 대시보드와는 **읽기 전용 조회로만** 연결되어, 복순이가 담당자의 기록을 바꿀 수 없습니다.

핵심 기능은 다섯 가지입니다. **① 어르신 맞춤 말벗 대화 ② 말하기·읽어 주기(음성) ③ 사례관리 기록 기반 안부 ④ 위기 상황 최우선 안내 ⑤ 담당자 승인·모니터링.** 그리고 이 모든 기능은 어르신의 개인정보를 지키는 장치(기기 등록 승인, 생년월일 확인, 서버 승인 확인, 이용 횟수 제한 등) 위에서 동작합니다.

***

> **④ Google OAuth 클라이언트를 만들고 Supabase에서 Google 로그인 제공자를 켭니다.** 관리자 화면(`/admin`)이 구글 계정으로 로그인합니다. (아래 **[Google OAuth 클라이언트 만들기]** 참고)<br>
> **⑤ `.env.local.example`을 `.env.local`로 복사해 값을 채웁니다.**<br>
> **⑥ `bun run dev`로 로컬 서버를 실행하고, 터미널에 표시되는 주소로 접속합니다.**<br>
> **⑦ Vercel에 저장소를 연결하고 아래 환경변수를 등록해 배포합니다.** 빌드와 출력 설정은 `vercel.json`에 들어 있습니다.

**[환경변수]**

각 항목은 **외부에 노출되면 안 되는 비밀값**이 포함되어 있습니다. 코드에 직접 입력하지 않고 `.env.local`(로컬) 또는 Vercel 환경변수(배포)에만 보관하며, `.env.local`은 GitHub에 올라가지 않습니다. 실제 값은 이 문서에 적지 않습니다.

```
# ── 공개해도 되는 값 (브라우저에도 전달됨) ──
VITE_SUPABASE_URL=                # Supabase 프로젝트 주소
VITE_SUPABASE_PUBLISHABLE_KEY=    # Supabase 공개(publishable/anon) 키
SUPABASE_URL=                     # 서버에서 쓰는 같은 주소
SUPABASE_PUBLISHABLE_KEY=         # 서버에서 쓰는 같은 공개 키

# ── 서버 전용 비밀값 ──
SUPABASE_SERVICE_ROLE_KEY=        # 서버 전용 서비스 키 (절대 공개 금지)
GEMINI_API_KEY=                   # 대화·읽어 주기에 쓰는 Gemini 키
ADMIN_EMAILS=                     # /admin에 들어갈 수 있는 구글 계정 (쉼표로 구분)

# ── 통합 사례관리 연동 (선택이지만 운영에는 권장) ──
CASE_LOOKUP_URL=                  # 사례관리 Supabase 프로젝트 주소
CASE_LOOKUP_ANON_KEY=             # 위 프로젝트의 공개(anon) 키. 반드시 같은 프로젝트의 것
CASE_LOOKUP_SECRET=               # 복순이와 사례관리가 나눠 가진 비밀값 원문
CASE_SERVICE_ROLE_KEY=            # (선택) 담당 복지사 전화번호를 읽는 데만 쓰는 서버 전용 키
COMPANION_API_KEY=                # 사례관리 대시보드가 복순이 분석 API를 부를 때 쓰는 키

# ── 담당자 표시 (비우면 "담당 사회복지사"로 보임) ──
STAFF_LEE_NAME=, STAFF_LEE_PHONE=, STAFF_LEE_TITLE=
STAFF_BAEK_NAME=, STAFF_BAEK_PHONE=, STAFF_BAEK_TITLE=

# ── 이용 횟수 제한 (선택) ──
UPSTASH_REDIS_REST_URL=, UPSTASH_REDIS_REST_TOKEN=   # Vercel KV 값(KV_REST_API_URL/TOKEN)도 인식
```

> **연동 환경변수(`CASE_LOOKUP_*`)가 비어 있으면** 복순이는 사례관리에서 어르신을 확인하지 않고 통과시킵니다(개발·시험 환경용). 운영에서는 반드시 설정하세요. **Upstash 값이 없으면 이용 횟수 제한이 모두 꺼집니다.** 서비스는 정상 작동하지만 남용을 막아 주는 장치가 없는 상태입니다.

**[Google OAuth 클라이언트 만들기]**

1. Google Cloud Console → API 및 서비스 → OAuth 동의 화면을 설정합니다(앱 이름, 지원 이메일).
2. 사용자 인증 정보 → OAuth 클라이언트 ID 만들기 → 유형은 **웹 애플리케이션**을 고릅니다.
3. **승인된 리디렉션 URI**에 `https://<프로젝트 ID>.supabase.co/auth/v1/callback`을 넣습니다.
4. 발급된 `<클라이언트 ID>`와 `<클라이언트 시크릿>`을 Supabase 대시보드 → Authentication → Sign In / Providers → Google에 입력하고 켭니다. (이 값들은 저장소나 `.env` 파일에 적지 않습니다.)
5. Supabase → Authentication → URL Configuration의 Site URL과 Redirect URLs에 배포한 서비스 주소(`https://<우리 기관 주소>`)를 등록합니다.

**[운영 보안 설정 (설치 후 꼭 확인)]**

* **신규 가입 끄기**: 복순이는 어르신이 Supabase 계정을 만들지 않고, `/admin`에는 `ADMIN_EMAILS`에 적은 구글 계정만 들어옵니다. 그래서 담당자(관리자) 계정으로 `/admin`에 한 번씩 로그인해 둔 뒤, Supabase → Authentication → Sign In / Providers의 **Allow new users to sign up**을 끄는 것을 권장합니다. 관리자를 새로 추가할 때만 잠시 켜서 그 계정이 로그인한 뒤 다시 끄세요. 끈 상태에서는 한 번도 로그인하지 않은 구글 계정은 `ADMIN_EMAILS`에 있어도 들어올 수 없습니다.
* **Gemini 예산 한도**: Google Cloud Console → 결제 → 예산 및 알림에서 월 예산과 알림(예: 50%·90%·100%)을 설정하고, API 할당량도 기관 규모에 맞게 낮춰 둡니다. 키가 유출되거나 호출이 폭증해도 요금이 한없이 늘지 않도록 하기 위함입니다. 이용 횟수 제한(Upstash)과 함께 써야 남용을 막을 수 있습니다.

**[연동 비밀값 설정 순서]**

사례관리 쪽 데이터베이스에는 비밀값의 **해시(SHA-256)만** 저장됩니다. 원문은 사례관리 쪽에서 새로 발급할 때 **딱 한 번만** 화면에 보이므로, 그 자리에서 복사해 복순이의 `CASE_LOOKUP_SECRET`에 넣습니다. 비밀값, 주소, 공개 키는 **같은 사례관리 프로젝트의 것으로 함께** 맞춰야 합니다. 맞지 않으면 사례관리가 `unauthorized`로 거절하며, 복순이 서버 로그에 비밀값의 지문(길이와 SHA-256 앞 8글자)이 남아 사례관리 쪽 해시와 비교해 볼 수 있습니다.

**[모니터링 함수 비밀값 설정 (필수)]**

사례관리 대시보드가 복순이 대화를 읽어 가는 두 함수(`companion_monitor_list`, `companion_monitor_detail`)는 비밀값이 맞아야만 동작합니다. 이 비밀값은 저장소에 들어 있지 않고, 마이그레이션 SQL에 `<COMPANION_MONITOR_SECRET을_여기에_입력>` 자리표시자로 되어 있습니다. **설치하는 기관이 직접 길고 무작위인 새 값을 정해야 하며, 정하지 않으면 두 함수는 `secret_not_configured`를 돌려주고 모니터링이 동작하지 않습니다.**

1. 길고 무작위인 비밀값을 새로 만듭니다. 다른 곳에 쓰던 값이나 예시 값은 쓰지 않습니다.
2. SQL Editor에서 `20260729160000_companion_monitor_rpc.sql`과 `20260902000000_companion_detail_include_id.sql`을 실행하기 **직전에**, 파일 안의 자리표시자(총 3곳)를 그 값으로 바꿉니다. **바꾼 파일은 저장소에 커밋하지 마세요.**
3. 사례관리 쪽 Supabase Edge Function 시크릿 `COMPANION_MONITOR_SECRET`에 **똑같은 값**을 넣습니다. 두 곳이 다르면 모니터링 화면이 `unauthorized`로 거절됩니다.
4. 값을 바꿀 때(교체)도 두 곳을 같은 시간대에 함께 바꿔야 모니터링이 끊기지 않습니다.
5. **공개 키로는 호출되지 않게 막습니다.** `20261102000000_companion_monitor_service_role_only.sql`이 두 함수의 실행 권한을 `anon`·`authenticated`에서 회수하고 `service_role`만 허용합니다. 사례관리 쪽 `companion-proxy`가 `COMPANION_SUPABASE_SERVICE_ROLE_KEY`로 호출하므로, **`companion-proxy`를 먼저 배포한 뒤 이 SQL을 실행하세요.** 순서가 반대이면 모니터링 화면이 멈춥니다.

**[정기 백업 (선택)]**

* **복구용**: `supabase/functions/backup-bokdori-data`를 배포하면 어르신 정보와 대화 기록이 JSON으로 Google Drive에 저장됩니다. 주기는 Supabase Cron으로 정합니다.
* **열람용**: `scripts/bokdori-drive-backup.gs`를 Google Apps Script에 붙여 넣고 일 단위 트리거를 걸면, 어르신별 스프레드시트(날짜·역할·내용)가 만들어지고 실패하면 메일로 알려 줍니다.

**기관에 맞게 바꿔야 하는 것**: 개인정보처리방침의 기관명·보호책임자·연락처(`src/routes/privacy.tsx`), 담당자 표시 환경변수, 백업 스크립트의 Drive 폴더 ID(`scripts/bokdori-drive-backup.gs`의 `UPLOAD_FOLDER_ID`)와 Supabase 주소(`SUPABASE_URL`)입니다.

#### 주요 기능

**1. 어르신 맞춤 말벗 대화**

*관련 기능 : AI 대화, 이름 부르기, 말투와 속도 조절, 빠른 답장, 날씨 안부*

복순이는 어르신이 편안하게 느끼는 존댓말로 천천히, 재촉하지 않고 대화합니다. 어르신 성함으로 부르고, 위치 사용을 허용한 기기에서는 날씨 안부로 대화를 엽니다. 마지막 대화로부터 한참 지나 다시 인사하시면 작별로 오해하지 않고 반갑게 맞이합니다. 말하기가 어려우면 **'네, 좋아요', '몸이 아파요'** 같은 빠른 답장을 누를 수 있고, 말벗의 이름과 글자 크기(3단계)를 바꿀 수 있습니다.

**2. 말하기와 읽어 주기**

*관련 기능 : 음성 입력(STT), 읽어 주기(TTS), 목소리·속도·음량 설정*

마이크 버튼을 누르고 말씀하시면 글자로 바뀌어 전달됩니다. 복순이의 답은 **'읽어 주기'** 버튼으로 들을 수 있고, 목소리는 5가지(활발한·부드러운·따뜻한·맑은·경쾌한), 속도는 3단계(천천히·보통·빠르게)로 고를 수 있습니다. 마이크가 막히는 환경(앱 안 브라우저 등)에서는 글자판으로 안내합니다.

**3. 사례관리 기록을 아는 말벗**

*관련 기능 : 읽기 전용 연동(`companion_lookup`), 대화 포인트 자동 생성, 담당자 확인 키워드*

사례관리 대시보드에서 어르신의 최근 상담, 주요 욕구, 목표, 제공받은 서비스를 **읽기 전용**으로 가져와 대화 맥락으로 씁니다. 기록에서 "그 이후 어떠세요?" 같은 화제 3~4개를 자동으로 골라 대화 흐름에서 자연스럽게 꺼냅니다. 담당 복지사가 정한 **확인 키워드(최대 3개, 예: 낙상·우울·치매)** 는 복순이가 직접 묻지 않고 "요즘 기분은 좀 어떠세요?"처럼 돌려서 안부로 확인하며, 이 키워드는 어르신 화면에 보이지 않습니다. 담당 복지사의 이름과 전화번호도 함께 가져와 **'담당 선생님 전화'** 버튼으로 바로 연결합니다.

**4. 위기 상황 최우선 안내**

*관련 기능 : 위기 대응 지침, AI 응답 실패 시 고정 안내문, 위기 키워드 분류*

어르신이 "죽고 싶다", "살기 싫다" 같은 말씀을 하시면 먼저 충분히 공감한 뒤 **자살예방상담전화 1393**을 안내합니다. 넘어졌거나 가슴·머리가 갑자기 아프다고 하시면 **119**를, 보이스피싱이 의심되면 **112와 금융감독원 1332**를 안내합니다. AI가 답하지 못하는 순간(서버가 바쁘거나 응답이 비었을 때)에도 이 안내가 끊기지 않도록, **마지막 말씀에 위기 신호가 있으면 화면이 고정 안내문을 직접 보여 줍니다.** 이 안내는 AI의 답변에 의존하지 않는 규칙 기반 장치입니다.

**5. 담당자 승인과 모니터링**

*관련 기능 : 기기 등록 승인, 관리자 화면, 대화·분석 모니터링 연동*

처음 쓰는 기기는 기관코드·성함·전화번호로 **등록을 요청**하고, 담당자가 `/admin`에서 **본인 확인 후 승인**해야 대화할 수 있습니다. 담당자는 승인·거절·승인 해제·삭제를 할 수 있고, 어르신의 접속 코드(고유번호)와 최근 접속 시각을 확인하며 대화 확인 키워드를 정합니다. 승인을 해제하면 그 기기는 곧 처음 화면으로 돌아가고 서버에서도 즉시 차단됩니다. 사례관리 대시보드는 읽기 전용 조회와 분석 API로 어르신별 대화 기록, 기분·위험도 요약, 위기 신호를 확인합니다.

**6. 개인정보를 지키는 장치**

*관련 기능 : 서버 승인 확인, 생년월일 확인, 이용 횟수 제한, 입력 검증, 정기 백업*

* **접근 통제** : 채팅·읽어 주기·대화 기록 조회는 모두 **서버가 승인된 등록을 확인한 뒤에만** 처리합니다. 등록 정보 테이블은 브라우저에서 직접 읽거나 쓸 수 없고 서버만 접근합니다. 재승인할 때는 승인한 등록이 어르신의 기존 대화를 이어받아, 승인 해제가 어느 기기에서든 똑같이 적용됩니다.
* **본인 확인** : 고유번호 4자리와 **생년월일 6자리**가 맞아야 기기가 어르신의 대화에 연결됩니다. 틀리게 반복하면 해당 IP에서 잠시 막힙니다(Upstash 설정 시).
* **입력 보호** : 서버는 받은 대화에서 어르신과 AI의 글자만 남기고(시스템 지시·파일 등은 버림), 길이를 제한하며, 어르신 성함은 DB 값을 우선 사용합니다. AI 응답이 40초 안에 오지 않으면 끊습니다.
* **기록 최소화** : 서버 로그에는 이름·전화번호·생년월일을 남기지 않고, 세션 ID는 앞 8자만 남깁니다.
* **보관과 백업** : 데이터는 Supabase에 저장되고, 정기 백업은 비공개 Drive 폴더에 보관합니다.

#### AI가 하지 않는 일 (사용 범위의 한계)

복순이는 어르신의 일상 대화와 안부를 나누는 말벗일 뿐, 돌봄 전문가나 의료인을 대신하지 않습니다.

| 하지 않는 일 | 이 솔루션에서의 방식 |
| :-- | :-- |
| 의료 진단·약 처방·법률 판단 | 하지 않습니다. "그런 건 담당 선생님께 꼭 여쭤보세요."라고 안내합니다. |
| 위험도·서비스 대상 판정 | AI가 판정하지 않습니다. 분석 결과의 위험도는 담당자를 위한 참고 의견이고, 사례관리 대시보드의 대상자 정보에 자동으로 반영되지 않습니다. |
| 사례관리 기록 수정 | 복순이는 사례관리 기록을 **읽기만** 합니다. 쓰거나 바꾸는 경로가 없습니다. |
| 정치·성적 화제·혐오 발언에 대한 동조 | 의견을 말하지 않고 가볍게 다른 화제로 돌립니다. |
| 심부름·검색·금전 요청 | "복순이가 도와드리기 어렵지만 가까운 분께 부탁해 보세요."라고 안내합니다. |
| 사람인 척하기 | "복순이는 AI예요."라고 솔직하게 말합니다. |
| 위기 상황을 담당자에게 자동 신고 | **하지 않습니다.** 위기 신호가 있는 대화는 담당자가 모니터링 화면에서 확인하며, 자동 전화·문자 알림은 아직 없습니다. (3.3 향후 계획 참고) |

AI는 틀릴 수 있습니다. 그래서 대화 내용을 담당 복지사가 볼 수 있다는 사실을 개인정보처리방침에 알리고, 위기 안내는 AI가 아니라 규칙으로 한 번 더 보장하며, 사용 중 발견한 오류는 기록해 고쳐 나갑니다.

**AI 성능 개선 시도**

**① "안녕"을 작별로 오해하는 문제 — 인사말 판단 기준을 프롬프트에 명시했습니다**<br>
저녁에 "안녕"이라고 인사하면 복순이가 작별 인사로 받아 대화를 끝내려는 오류가 있었습니다. 시간대와 상관없이 "안녕"은 인사로 받고, 마지막 대화로부터 6시간 이상 지났다면 **'오랜만의 대화'로 보고 반갑게 맞이하며 안부를 묻도록** 지침을 추가했습니다.

**② 사례관리 기록을 대화 화제로 바꾸기 — '대화 포인트' 자동 생성**<br>
상담 요약을 통째로 전달했더니 복순이가 기록을 읽는 듯한 말투가 되거나 같은 화제만 반복했습니다. 코드가 최근 상담, 주요 욕구, 진행 중인 목표, 최근 제공한 서비스에서 **구체적인 화제 3~4개를 골라 맨 위에 두고**, 기록을 낭독하지 않고 자연스럽게 하나씩 꺼내도록 했습니다.

**③ 위기 대응을 AI에만 맡기지 않기 — 규칙 기반 고정 안내문**<br>
위기 대응 지침은 프롬프트의 가장 중요한 부분에 두었지만, AI 서버가 바쁘거나 응답이 비면 안내 자체가 나가지 않는다는 점을 발견했습니다. 마지막 말씀에 위기 키워드가 있으면 **AI가 답하지 못하는 순간에도 화면이 119 또는 1393 안내를 직접 보여 주도록** 했습니다. 키워드는 띄어쓰기와 말 모양 변화("아파요", "죽고 싶어")까지 잡도록 시험으로 확인했습니다.

**④ 담당자가 정한 주제를 어르신에게 직접 묻지 않기**<br>
담당 복지사가 낙상·우울 같은 확인 키워드를 정하면, 복순이가 "치매 있으세요?"처럼 직접 묻는 것이 아니라 "뭘 어디 뒀는지 자꾸 잊어버리시진 않아요?"처럼 일상의 질문으로 바꿔 묻도록 예시와 함께 지침을 주었습니다.

### 2.3 이용자용 가이드

**이용 전 준비사항**

별도 프로그램 설치는 필요하지 않습니다. 스마트폰이나 컴퓨터의 웹 브라우저만 있으면 됩니다. 처음 쓰는 기기는 **담당 복지사의 승인**을 받아야 하며, 승인되기 전에는 대화할 수 없습니다. 스마트폰에서는 브라우저 메뉴의 **'홈 화면에 추가'** 를 선택하면 앱처럼 바로 실행할 수 있습니다.

**실제 이용 방법**

1. 처음 쓰는 기기라면 담당 복지사의 도움을 받아 기관코드, 어르신 성함, 전화번호를 입력해 **등록을 요청**합니다. 사례관리에 등록된 어르신이어야 요청이 접수됩니다.
2. 담당 복지사가 확인하고 승인하면 화면이 자동으로 대화 화면으로 넘어갑니다. (승인 대기 화면에서 기다리시면 됩니다.)
3. 다음부터는 첫 화면에서 **고유번호 4자리와 생년월일 6자리**를 입력해 접속합니다. **'로그인 상태 유지'** 를 켜 두면 홈 화면 아이콘을 눌러 바로 들어갑니다.
4. 아래의 **'눌러서 말하기'** 버튼을 누르고 말씀하시거나, 글자판에 직접 적어서 보냅니다. 말하기가 어려우면 **빠른 답장**을 눌러도 됩니다.
5. 복순이의 답 옆 **읽어 주기** 버튼을 누르면 소리로 들을 수 있습니다. 소리가 작거나 빠르면 설정 화면에서 목소리·속도·음량과 글자 크기를 바꿀 수 있습니다.
6. 몸이 아프거나 마음이 힘들 때는 **'담당 선생님 전화'** 버튼으로 바로 전화하실 수 있습니다.

**이용 시 주의사항**

* 복순이는 사람이 아니라 **AI**입니다. 의사나 법률 전문가를 대신하지 않으며, 건강이나 법에 관한 판단은 담당 선생님께 물어보세요.
* **위급할 때는 복순이에게 묻지 말고 바로 119에 전화하세요.** 마음이 많이 힘드실 때는 자살예방상담전화 1393(24시간)에 전화하실 수 있습니다.
* 어르신과 복순이의 대화는 **담당 사회복지사가 안전을 확인하기 위해 볼 수 있습니다.** (개인정보처리방침의 '3. 담당 복지사의 확인과 AI 이용 안내'에 안내되어 있습니다.)
* 카카오톡·네이버 앱 안에서 열면 음성 입력과 홈 화면 추가가 안 됩니다. 이때는 화면의 안내대로 **크롬·사파리 같은 브라우저로 다시 열어 주세요.**
* 지원 환경: 아이폰·아이패드는 iOS 16.4 이상, 안드로이드는 크롬 111 이상(삼성 인터넷 22 이상), PC는 크롬·엣지 111 이상, 파이어폭스 128 이상, 사파리 16.4 이상입니다. 파이어폭스는 음성 입력이 지원되지 않아 글자판으로 안내됩니다.

### 2.4 관리자용 가이드

#### 솔루션 구조 및 사용 기술

```
[어르신 기기 (웹/PWA)]
    ↓ 고유번호 + 생년월일로 접속, 처음이면 등록 후 담당자 승인
[복순이 (bright-day-talk)]  ── 대화·읽어 주기 ──▶  Google Gemini
    ↓ companion_lookup RPC (읽기 전용)
[통합 사례관리 대시보드 (ai-case-management)]
    → 케어 정보 → 복순이 DB에 저장 → 대화 맥락으로 활용
    ← 사례관리 대시보드가 복순이의 모니터링 RPC·분석 API를 읽어 대화 확인
```

| 역할 | 서비스 |
| :----------- | :----------------------- |
| 화면 구성·서버 함수·배포 | TanStack Start (React 19, Vite) + Vercel (코드 푸시 시 자동 배포) |
| 데이터베이스·인증 | Supabase (PostgreSQL, Google OAuth) |
| AI 대화·음성 합성 | Google Gemini API (Vercel AI SDK) |
| 이용 횟수 제한 | Upstash Redis (선택) |
| 정기 백업 | Supabase Edge Function + Google Drive (Apps Script 중계) |
| 스타일 | Tailwind CSS 4 |

#### 담당자(관리자)용

**기기 등록 승인**

1. 허용된 구글 계정(`ADMIN_EMAILS`)으로 `/admin`에 로그인합니다.
2. **'승인 대기'** 목록에서 기관, 성함, 요청 시각을 확인하고, 사례관리 담당자와 **실제 어르신이 맞는지 본인 확인**을 거칩니다.
3. 맞으면 승인, 아니면 거절(사유 입력)합니다. 승인된 기기는 곧 대화 화면으로 넘어갑니다.
4. 같은 어르신이 새 기기에서 다시 승인되면 **이전 대화가 이어지고**, 이전 기기의 등록은 정리됩니다.
5. 퇴원·사망·서비스 종료 등으로 더는 쓰면 안 될 때는 **승인 해제** 또는 삭제를 합니다. 해제하면 그 기기는 곧 처음 화면으로 돌아가고 서버에서도 대화가 막힙니다.
6. 등록을 삭제하면 **등록 신청 정보만** 지워집니다. 대화 내용과 사례관리에서 가져온 정보는 자동으로 지워지지 않으니, 삭제 요청이 있으면 따로 처리해야 합니다.

**대화 확인 키워드**

승인된 어르신마다 담당자가 최대 3개의 키워드(예: 낙상, 우울)를 정할 수 있습니다. 복순이가 대화 중에 이 주제를 자연스럽게 확인하며, 키워드는 어르신 화면에 보이지 않습니다.

**운영 중 신경 써야 할 사항**

* **환경변수를 바꾼 뒤에는 다시 배포해야 반영됩니다.** Vercel은 변경 이후에 빌드한 배포부터 새 값을 씁니다. `Sensitive`로 저장하면 값을 다시 볼 수 없으니, 바꿀 때는 덮어쓰고 서버 로그의 지문으로 확인하세요.
* **사례관리 연동 확인**: 어르신이 앱을 열 때 서버 로그에 `[care-link] 동기화 완료`가 남습니다. `unauthorized`가 나오면 비밀값·주소·공개 키가 같은 사례관리 프로젝트의 것인지 먼저 확인하세요.
* **Gemini 모델 점검**: 모델은 정기적으로 교체·종료될 수 있습니다. AI가 갑자기 안 되면 모델 종료(404)나 API 키·결제 상태를 먼저 확인하세요. 대화가 길어지면 AI에는 최근 40건만 전달합니다.
* **이용 횟수 제한**: 채팅은 세션당 분당 30회, 읽어 주기는 분당 20회, 생년월일 확인은 IP당 10분 30회(같은 번호를 5번 틀리면 30분 잠금)입니다. Upstash 환경변수가 없으면 모두 꺼집니다.
* **Supabase 플랜**: 무료 플랜은 비활성 시 프로젝트가 일시 정지되어 서비스 전체가 멈출 수 있습니다. 장기 운영 시 유료 플랜이나 정기 백업을 권합니다.
* **등록 테이블 접근 정책**: `worker_registrations`는 **서버(service_role)만** 읽고 씁니다. 브라우저(anon)에 읽기·쓰기 정책을 열면 어르신의 이름·전화번호·세션 ID가 공개 키만으로 노출되므로 절대 만들지 마세요. (2026-10-30부터 Supabase는 새 테이블에 명시적인 `GRANT`가 필요합니다. 마이그레이션 견본에 반영되어 있습니다.)
* **담당자 계정 관리**: 관리자 구글 계정에는 2단계 인증을 적용하고, 퇴직 시 `ADMIN_EMAILS`에서 바로 빼 주세요.

#### 시스템 관리자(IT 담당자)용

코드를 수정해 GitHub에 push하면 Vercel이 자동으로 재배포합니다. 데이터베이스 변경이 필요하면 `supabase/migrations`에 SQL을 추가해 Supabase SQL Editor에서 실행합니다. 백업 Edge Function은 `npx supabase functions deploy backup-bokdori-data --project-ref <프로젝트 ID>`로 배포하고, 함수 시크릿(`DRIVE_UPLOAD_URL`, `DRIVE_SECRET`)은 Supabase 대시보드에 등록합니다. 코드와 이 문서에는 실제 키 값을 적지 않습니다.

## 3. 임팩트 계획서

### 3.1 현장 적용 결과

복순이는 **아직 실제 어르신을 대상으로 운영하기 전 단계**입니다. 시스템은 구축했고, 사례관리 담당자와 개발자가 시험 계정으로 등록 → 승인 → 대화 → 사례관리 연동의 흐름을 점검하고 있습니다. 어르신 이용 결과에 대한 수치나 후기는 아직 없으며, 이 문서에 확인되지 않은 효과는 적지 않았습니다.

지금까지 확인한 것은 다음과 같습니다.

* 사례관리에 등록된 어르신의 기록(최근 상담·욕구·목표·제공 서비스)이 복순이의 대화 맥락으로 들어가고, 담당 복지사의 이름과 전화번호가 화면의 전화 버튼으로 이어지는 것
* 승인 해제와 재승인이 서버에서 일관되게 적용되고, 승인받지 않은 기기는 대화·읽어 주기·기록 조회가 모두 막히는 것
* 서버 승인 확인, 생년월일 확인 제한, 입력 검증, 위기 키워드 분류, 백업 스크립트를 가짜 데이터로 시험해 통과한 것

실제 어르신 대상 시범 운영은 담당자 점검과 동의서 절차를 마친 뒤 진행할 계획입니다.

***

### 3.2 시행착오와 개선

**① 사례관리 연동이 거절되던 문제 — 비밀값이 아니라 '어느 프로젝트를 부르는가'가 원인이었습니다**

복순이가 사례관리를 조회할 때마다 `unauthorized`로 거절되어 어르신 정보가 연결되지 않았습니다. 비밀값을 여러 번 바꿔 보았지만 해결되지 않았고, 서버 로그에 **비밀값의 지문(길이와 SHA-256 앞 8글자)** 을 남기도록 해 사례관리 DB의 해시와 직접 비교했습니다. 그 결과 값은 일치했고, **배포 환경의 사례관리 주소가 다른 프로젝트를 가리키고 있는 것**이 원인이었습니다. 비밀값을 드러내지 않고 일치 여부만 확인하는 방식이라, 운영 중에 같은 일이 생겨도 원인을 좁힐 수 있습니다.

**② 등록 정보가 공개 키만으로 읽히던 구멍 — 점검에서 발견하고 닫았습니다**

AI와 사람 검토로 보안을 점검하다가, 승인 대기 화면이 브라우저에서 등록 테이블을 직접 읽도록 만들어져 있어 **운영 DB에 누구나 읽고 쓸 수 있는 정책**이 열려 있었던 것을 확인했습니다. 이름·전화번호·세션 ID가 공개 키만으로 읽힐 수 있는 상태였습니다. 승인 상태 확인을 서버 함수로 옮기고 정책과 권한을 모두 삭제했으며, 같은 일이 반복되지 않도록 마이그레이션에 경고를 남겼습니다.

**③ 재승인하면 승인 해제가 안 먹히던 문제 — 승인한 등록이 대화를 이어받도록 바꿨습니다**

어르신이 새 기기에서 재승인되면, 기기가 이전 세션으로 바뀌어 승인 확인이 옛 등록을 보게 되고 새 등록을 해제해도 접속이 이어질 수 있었습니다. 인증 없이 세션을 알려 주던 조회 기능도 함께 있었습니다. 이제 **관리자가 승인하는 순간 서버가 이전 세션을 이어받게 하고**, 모든 확인이 그 등록 하나를 기준으로 하도록 정리했습니다.

**④ 위기 안내가 AI에만 달려 있던 문제 — 규칙으로 한 번 더 보장했습니다**

위기 대응 지침은 프롬프트에 있었지만, AI 서버가 바쁘거나 응답이 비면 안내 없이 "잠시 문제가 생겼어요"만 보였습니다. 마지막 말씀의 위기 키워드를 규칙으로 가려 **AI가 답하지 못할 때 119·1393 안내를 화면이 직접 보여 주게** 했습니다. 시험에서 "가슴이 아파요" 같은 활용형이 목록에서 빠진 것을 발견해 보완했습니다.

**⑤ 기기별 문제 — 아이폰 읽어 주기, 앱 안 브라우저**

아이폰에서는 Safari의 재생 제한 때문에 읽어 주기 소리가 나지 않았습니다. 버튼을 누른 순간 0.1초의 무음을 먼저 재생해 제한을 풀도록 했고, 음량은 아이폰 웹에서 바꿀 수 없어 설정 화면에서 안내문으로 대신했습니다. 카카오톡·네이버 앱 안 브라우저에서는 마이크가 막혀, 첫 화면에 "다른 브라우저로 열어 주세요" 안내를 띄웁니다.

**⑥ 남아있는 한계**

5장의 '알려진 한계'를 참고해 주세요. 가장 큰 한계는 **실제 어르신 이용 경험을 아직 확인하지 못했다는 점**입니다. 어르신의 말투와 화제는 개인마다 다르므로, 시범 운영에서 대화의 자연스러움과 위기 판단의 적절함을 확인하고 지침을 계속 고쳐 가야 합니다.

### 3.3 향후 계획 및 임팩트 확산

**단기 계획 (2026년 내)**

담당자 시험을 마무리하고, 동의서 절차를 갖춘 소수의 어르신과 **시범 운영**을 시작합니다. 위기 신호가 있는 대화를 **담당자에게 자동으로 알려 주는 기능**(예: 알림)을 추가해, 모니터링 화면을 열어 보지 않아도 급한 상황이 전달되도록 합니다. 위기 키워드는 시범 운영 기록을 보며 보완하고, 자동 시험을 저장소에 갖추어 수정이 쌓여도 안전하게 고칠 수 있도록 합니다.

**중기 계획 (2027년)**

시범 운영 결과를 바탕으로 대화 품질과 안내 문구를 다듬고, 중랑구 내 유관기관으로 확산을 추진합니다. 기관코드와 승인 구조가 이미 갖춰져 있어 **신규 기관 추가 시 별도 개발 없이 적용**할 수 있도록 설치 가이드와 마이그레이션을 정리합니다.

**장기 비전**

고령화 사회에서 혼자 사시는 어르신은 계속 늘고, 담당자 한 사람이 돌볼 수 있는 인원에는 한계가 있습니다. 복순이가 지향하는 것은 AI가 담당자를 대신하는 것이 아니라, **어르신에게는 말 걸 수 있는 말벗이 되고, 담당자에게는 어르신의 오늘을 전해 주는 것**입니다. 사례관리 대시보드와 복순이가 서로 이어져, 기록이 어르신을 돕는 대화로 돌아가고 어르신의 이야기가 다시 기록으로 쌓이는 **쌍방향 돌봄 모델**을 전국 복지관에 확산 가능한 형태로 만들어 가겠습니다.

### 4.5 개인정보·AI 윤리 항목

1. 어떤 개인정보를 모으고, 어디에 쓰고, 어디로 보내는지 설명해 주세요.

   등록할 때 **성명, 전화번호, 기관코드, 생년월일 6자리(본인 확인용)** 를 받고, 사례관리 시스템에서 담당 복지사가 기록한 **성별, 담당 복지사, 위험도, 주요 욕구, 주거·복지 상태, 상담 기록 요약, 목표, 제공 서비스**를 읽기 전용으로 가져옵니다. 이용하면서 **기기 식별 정보(세션 ID), 대화 내용, 접속 일시, AI가 대화를 정리한 분석 결과**가 생기고, 등록 신청 때는 IP 주소와 기기 종류가 자동으로 기록됩니다. 목소리·속도·글자 크기 같은 설정과 프로필 사진은 이용 중인 기기에만 저장하고 서버로 보내지 않습니다. 이 정보는 **말벗 대화 제공, 본인 확인과 기기 승인, 사례관리 기록을 참고한 맞춤 대화, 담당 복지사의 안전 확인**에 씁니다. 데이터는 **Supabase에 저장**하고, 대화를 만들 때는 대화 내용과 사례관리 기록 요약, 어르신 성함이 **Google Gemini API로 전송**됩니다(국외 서버를 거칠 수 있음). 이용 횟수 제한을 위해 세션 ID와 IP가 Upstash에서 일시 처리되며, 날씨 안부는 위치를 허용한 기기에서 위도·경도가 날씨 서비스(Open-Meteo)로 바로 전송됩니다(복순이 서버에는 저장하지 않음). 이 모든 내용은 서비스 안의 개인정보처리방침(`/privacy`)에 안내하고 있습니다.

2. 개인정보를 수집·활용했다면, 이용자의 동의를 받았는지 또는 동의 없이 써도 되는 근거가 무엇인지 설명해 주세요.

   복지관은 어르신이 제출한 **'AI 기능 활용 동의서'에 따라 개인정보를 처리**합니다(「개인정보보호법」 제15조제1항제1호). **동의서를 제출한 어르신만 등록·승인되어 서비스를 이용**할 수 있도록 담당자 승인 절차를 두었습니다. 사례관리 기록은 기관이 서비스 제공을 위해 기존 절차로 수집한 정보를 읽기 전용으로 활용하며, 복순이가 새로 수집하는 정보는 위 항목에 한정됩니다. 동의를 철회하거나 삭제·열람·처리 정지를 원하면 보호책임자에게 요청할 수 있고, 삭제 요청 시 데이터베이스와 백업 파일에서 함께 파기합니다.

3. 개인정보를 어떻게 처리하는지, 그리고 AI를 사용한다는 사실을 이용자에게 어떻게 알리는지 설명해 주세요.

   개인정보는 Supabase PostgreSQL에 저장되고, 서버에서만 접근합니다. **승인된 기기만** 대화와 기록 조회가 가능하며, 데이터베이스 접근 키는 서버에서만 쓰고 이용자 화면에 노출하지 않습니다. 서버 로그에는 이름·전화번호·생년월일을 남기지 않습니다. AI 사용 사실은 **서비스 안의 개인정보처리방침 페이지**에서 "복순이는 사람이 아니라 생성형 인공지능(Google Gemini)이 답하는 서비스"라고 알리고, 어르신이 사람이냐고 물으시면 **"복순이는 AI예요."라고 솔직하게 답하도록** 지침을 두었습니다. 대화 내용을 담당 복지사가 안전 확인을 위해 볼 수 있다는 점과, 담당자가 정한 주제를 복순이가 대화 중에 자연스럽게 여쭤볼 수 있다는 점도 방침에 안내합니다.

4. AI가 틀리거나 부적절한 답을 했을 때, 사람이 확인하고 고칠 수 있는 절차가 있는지 설명해 주세요.

   어르신과 복순이의 **모든 대화는 저장되어 담당 복지사가 모니터링 화면에서 확인**할 수 있고, AI가 정리한 분석 결과(기분, 위험도 참고 의견, 위기 신호)도 함께 볼 수 있습니다. 부적절한 답변이 발견되면 담당자가 프롬프트(지침)를 고치고, 특정 어르신에게 문제가 있으면 **관리자 화면에서 승인을 해제**해 곧바로 대화를 막을 수 있습니다. 담당자는 어르신별 확인 키워드를 정해 복순이가 필요한 안부를 놓치지 않게 할 수 있습니다. 다만 현재는 **부적절한 답변을 담당자가 실시간으로 받는 알림이 없어서**, 모니터링 화면을 열어 확인해야 합니다. 이 점은 향후 보완할 과제입니다.

5. AI 사용으로 이용자가 실제로 피해를 볼 수 있는 상황을 어떻게 막고 있는지 설명해 주세요.

   복순이는 **의료 진단·약 처방·법률 판단을 하지 않도록** 지침을 두었고, 건강이나 법에 관한 판단은 담당 선생님께 안내합니다. 어르신이 위급하거나 마음이 힘든 말씀을 하시면 **119와 1393을 가장 먼저 안내**하고, AI가 답하지 못하는 순간에도 **규칙으로 가린 위기 키워드에 따라 고정 안내문을 화면이 직접 보여 줍니다.** 보이스피싱이 의심되면 송금하지 말라고 안내하고 112와 1332를 알립니다. 정치 의견, 성적 화제, 혐오 발언에 대한 동조는 하지 않고, 사람인 척하지 않으며, 과하게 의존하시면 담당 복지사나 가족과의 연결을 권합니다. 사례관리 기록은 **읽기만** 하고 바꿀 수 없으며, 서버는 대화 입력을 어르신과 AI의 글자로 걸러내고 길이를 제한합니다. 승인받지 않은 기기는 대화와 기록 조회가 모두 막힙니다. **Gemini는 결제(유료) 등급 키일 때만 전달된 대화 내용이 모델 학습에 사용되지 않는 것으로 안내**되며, 무료 등급이면 학습에 쓰일 수 있어 운영 기관이 키 등급을 확인해야 합니다.

* **세션 ID가 사실상 토큰입니다.** 복순이는 어르신이 매번 로그인하지 않도록 기기마다 세션 ID를 만들어 대화에 연결합니다. 이 값이 유출되면(예: 사용자가 다른 사람에게 보여 준 주소창) 그 어르신의 대화에 접근할 수 있습니다. 이 구조는 유지하고, 유출 경로(요청 주소, 로그, 공개 테이블)를 막는 쪽으로 보완해 왔습니다.
* **본인 확인이 생년월일 6자리입니다.** 약한 비밀이라, 횟수 제한(Upstash)이 켜져 있어야 의미가 있습니다. 같은 IP의 반복 시도는 막지만, 여러 IP를 쓰는 대입 공격까지 막지는 못합니다.
* **AI에 전송되는 범위**: 어르신 성함, 대화 내용, 사례관리 기록 요약이 Gemini로 전송됩니다. 사례관리 대시보드와 달리 **이름을 고유번호로 바꾸지 않습니다.** 어르신을 이름으로 부르는 말벗이기 때문입니다.
* **위기 대응의 한계**: 위기 안내는 AI의 답변과 규칙 기반 고정 안내문의 두 겹이지만, 담당자에게 **자동으로 알려 주는 기능은 아직 없습니다.** 위기 키워드는 말의 변형을 모두 잡지 못할 수 있어, 시범 운영 기록을 보며 보완해야 합니다.
* **실제 어르신 이용 검증 전**: 대화의 자연스러움과 위기 판단의 적절함은 가짜 데이터와 담당자 시험으로만 확인했습니다.
* **자동 시험 부족**: 저장소에 자동 시험이 없어, 수정이 쌓일 때 회귀를 사람이 확인해야 합니다.
* **설치 재현성**: 빈 DB 적용 시험은 통과했습니다. 실제 Supabase 프로젝트에서의 전체 동작은 설치 기관이 확인해야 합니다.
* **기기·브라우저**: 앱 안 브라우저(카카오톡·네이버)에서는 음성 입력이 안 되고, 아이폰 웹은 음량을 바꿀 수 없으며, 파이어폭스는 음성 입력이 지원되지 않습니다.
* **의존성 점검**: 빌드·개발 도구를 중심으로 알려진 취약점이 보고된 라이브러리가 남아 있습니다(대부분 배포된 서비스에는 포함되지 않습니다). 정기적인 점검과 업데이트가 필요합니다.
